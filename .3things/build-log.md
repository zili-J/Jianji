## 2026-09-13 行高作用于显示行 + 行号不重复

- 用户反馈：行高要调节“显示效果的行”（含段落内自动换行的行），而不是“记录的行数”；并且行号在内容折叠/换行时不要重复，只需在每条记录行的第一显示行标注。
- 做法：把行高换算成 Tk 的三段间距——设 `extra = line_height - 字体自然行高`，则段内换行间距 `spacing2 = extra`，段首/段尾补白 `spacing1 + spacing3 = extra`。这样 n 个显示行的总高恰为 `n × line_height`，自动换行的续行也会跟着变高。
- 标题留白随行高同比放大（`head_gap = max(4, spacing2)`），避免只放大正文导致标题与正文比例失衡。
- 行号重绘改为按“显示行”遍历：用 `dlineinfo` 逐显示行取纵向位置，只在该显示行所属逻辑行号与上一个已标注行号不同时才画，续行自动跳过。
- 新增 `app/main.py` 中的 `_font_linespace()`、`_line_metrics()`；`_apply_typography()` 统一设置 `spacing1/2/3`；`_redraw_line_numbers()` 用 `last_shown` 去重。

### 2. 修复整体字体发虚：进程未声明 DPI 感知

- 用户反馈「字体显示有些模糊，边缘不清晰」——不是某个字体的问题，是整个界面都虚。
- 定位：本机显示器 **2560×1600 / 150% 缩放**（`dmLogPixels = 144`），
  而进程 `GetProcessDpiAwareness` 返回 **0（未感知）**。未声明感知时 Windows 会把
  整个窗口**位图放大 1.5 倍**，文字边缘因此发糊；进程还被系统「骗」着以为屏幕是
  1707×1067、DPI 只有 96。
- 修法：启动时（建任何窗口之前）调用 `SetProcessDpiAwareness(2)` 声明 per-monitor DPI 感知，
  并读取真实 DPI 得到缩放比例 `SCALE`；再用 `px()` 把所有硬编码尺寸从逻辑像素换算成物理像素。
- 关键细节：Tk 的 `tk scaling` **只会自动缩放「以磅为单位」的字体**（感知后 Tk 自己把它
  设成 2.0），像素尺寸——包括编辑器的负数字号 `-size`——必须自己换算，否则界面会
  文字大、留白小，挤在一起。
- 覆盖范围：窗口尺寸与最小尺寸、三栏宽度（NAV_W/CARDS_W/GUTTER_W）、各处 padding、
  树行高、滑块长度、卡片几何与圆角、设置/字体窗口尺寸，以及编辑器、标题、代码块、
  行号、卡片的所有像素字号。

## 2026-09-20 扩充 Markdown 语法（全部输入即预览）

### 支持的语法

| 类别 | 语法 | 渲染效果 |
| --- | --- | --- |
| 标题 | `#` ~ `######` | 与正文同字号 + 加粗 + 左侧 H1–H6 徽标 |
| 分隔线 | `---` / `***` / `___` / `- - -` | 隐藏源码，画一条横线 |
| 引用 | `>` / `>>` | 隐藏 `>`，文字变灰 + 左侧竖条（换行续行连成一条） |
| 无序列表 | `-` / `*` / `+`，两空格一层 | 隐藏标记，按层级画实心圆 / 空心圆 / 方块 |
| 有序列表 | `1.` / `12)` | 隐藏源码，序号右对齐画在正文左侧 |
| 任务列表 | `- [ ]` / `- [x]` | 隐藏源码，画方框 / 方框加蓝色对勾 |
| 围栏代码块 | ` ``` ` … ` ``` ` | 隐藏围栏，等宽字体 + 浅灰底色 |
| 行内代码 | `` `x` `` | 等宽 + 浅灰底色 |
| 粗体 | `**x**` / `__x__` | 加粗 |
| 斜体 | `*x*` / `_x_` | 斜体 |
| 删除线 | `~~x~~` | 加删除线 |
| 高亮 | `==x==` | 加浅黄底色 |
| 链接 | `[文字](url)` | 隐藏方括号与 URL，文字变蓝加下划线 |
| 图片 | `![说明](url)` | 隐藏方括号与 URL，说明文字变灰斜体 |

全部都是「输入即预览」：不存在源码/预览模式切换。语法记号平时被 `elide` 隐藏，
光标落在哪一行，那一行的记号就显示出来（灰色）方便修改——这条规则对所有新语法一致。

### 实现结构

- 新增模块级的块级解析 `parse_block(line) -> LineInfo`，以及 `HEADING_RE` /
  `HR_RE` / `FENCE_RE` / `QUOTE_RE` / `TASK_RE` / `BULLET_RE` / `ORDERED_RE` /
  `INLINE_CODE_RE` / `LINK_RE` / `EMPHASIS_PATTERNS` 一组正则。
  判定顺序是刻意的：**分隔线要排在无序列表前面，任务列表也要排在无序列表前面**，
  否则 `***` 和 `- [ ]` 会被误判。
- `_apply_markdown_styles()` 重写：先做块级（标题/引用/列表/代码块），再做行内。
  行内用 `claimed` 区间记账，先匹配到的优先——这样 `` `**x**` `` 里的星号不会被当成粗体。
- 列表缩进用 `li0`–`li4` 五个标签，`lmargin1 == lmargin2 == 缩进`，
  标记被隐藏后正文和自动换行的续行都对齐到同一位置（悬挂缩进）。
- 左侧装饰（项目符号、复选框、序号、引用竖条、分隔线）用**画布池**绘制：
  每个装饰一块只占一小块的小画布，用完归还，而不是一整块覆盖层——
  整块覆盖会把正文盖住。有序序号右对齐到正文左侧 gap 处，项目符号同理。
- 复选框和项目符号都用 canvas 图元（oval / rectangle / line）画，不用 `☐`/`•`
  这类字符：不依赖字体是否收录该字形，缩放也不会糊。
- 卡片摘录 `_card_excerpt()` 改为复用 `parse_block`，保证「卡片上看到的」和
  「编辑区渲染的」对同一份语法理解一致。

### 三个坑（都很有代表性）

1. **Tk 的 Text 控件用 `\r` 作行分隔符。** `editor.get("3.0", "3.end")` 取回来的
   是 `'---\r'`，而 `HR_RE` 结尾是 `$`，于是分隔线被判成普通正文，横线画不出来。
   修法：`parse_block()` 开头 `line.rstrip("\r\n")`。**凡是靠行尾锚定的正则，
   都要先想到这一点。**
2. **`str.splitlines()` 不只按 `\r\n` 断行。** 它还会在 `\x0b`、`\x0c`、`U+2028`
   等处断开，而这些字符在 Text 控件里只是普通字符——行号会和控件的实际行数错位，
   样式套到错误的行上。改用 `re.split(r"\r\n|\r|\n", text)`。
3. **覆盖层画布的堆叠顺序。** 标题徽标画布是整高不透明的，会把落在同一横坐标
   范围内的项目符号盖住。装饰画布必须在徽标画布之后 `tk.Misc.lift()`，
   所以 `_redraw_margins()` 的调用顺序是有意义的（先徽标、后装饰）。

## 2026-09-20 表格语法 + 语法配色

### 做了什么

两件事：补上**表格**这一块最缺的语法，并把**单一灰色**换成一套分角色的配色。

此前的问题很直接：说明文档里的快捷键表在软件里就是一串带竖线的灰字，
既看不出是表格，也很难读；而标题、链接、代码、引用全是一个模子印出来的灰，
层级和类型只能靠读内容去猜。

### 表格

按 GFM 竖线表格实现。

- `_split_row()` 拆一格：两侧竖线可省；单元格里的 `\|` 先占位再还原，所以格子里能写竖线。
  **两侧带框的形式哪怕只有一个格子也算表格行**（`| 1 |`），否则单列表格没法用——
  这个坑是写测试时才发现的。
- `_table_separator()` 读分隔行，`:` 的位置决定每列对齐（`left`/`center`/`right`/`none`）。
- `collect_tables()` 扫全篇，判定条件是「这一行有竖线 **且下一行是合法分隔行**」，
  这样正文里偶尔出现的竖线不会被误判。表头列数取 `max(表头格数, 分隔行格数)`，
  数据行短了补空、长了截断，表格不会被撑歪。
- 表格是**跨行**语法，所以 `_apply_markdown_styles()` 改成分两遍走：
  第一遍只算「哪些行在围栏代码块里」「哪些行属于表格」，第二遍才逐行套样式。
  否则代码块里的竖线会被当成表格，表格也会依赖尚未确定的行号。
- 编辑区渲染：表头加粗 + 深蓝字 + 浅蓝底；数据行隔一行铺一层极淡底色（斑马纹）；
  行分隔线、上下外框、左右外框用**画布细线**画。
- 表格行不给列表装饰（`_decoration_spec` 对 `kind == "table"` 返回 None）。

### 配色

不再是满屏一个灰，各个角色有自己的颜色（`HEADING_COLORS`、`BULLET_COLORS`、
`CODE_TEXT`、`LINK_COLOR`、`IMAGE_COLOR`、`QUOTE_TEXT`、`QUOTE_BAR_COLOR`、
`TASK_CHECK_COLOR`、`TABLE_*` 一组）：

| 元素 | 变化 |
| --- | --- |
| H1–H6 | 深蓝 → 墨绿六级渐变，颜色成为继加粗、徽标之后的第三种层级线索 |
| 粗体 / 斜体 | 深蓝 / 冷灰蓝 |
| 删除线 | 文字转浅灰 |
| 高亮 | 浅黄底 + 琥珀色文字（此前只有底色，浅底上的黑字对比不够） |
| 行内代码 / 代码块 | 洋红字 + 浅灰底 / 冷灰字 + 浅灰底 |
| 图片说明 | 灰 → 紫，与蓝色链接区分开 |
| 引用 | 冷灰蓝字 + 更粗的淡蓝竖条（2px → 3px） |
| 项目符号 | 每层一色（蓝/绿/橙/紫），第二层空心圆描边加粗 |
| 有序序号 | 蓝色加粗 |
| 任务列表 | 勾选后整格填绿 + 白勾，扫一眼就知道做完没有 |
| Markdown 记号 | `MUTED` → 更浅的 `SYNTAX_COLOR`，不抢正文注意力 |

### 踩到的坑

- **Tk 的 Canvas 是不透明的。** 直觉写法是「一块整表大小的画布，画上外框和网格线」，
  结果整张表的内容全被白底盖掉——截图里只剩一个空框。改法：边框**只由几条细线组成**，
  每条线占一块只够放下这条线的小画布，线之间的空隙留给正文。
  已加测试 `test_frame_is_made_of_thin_lines_not_a_slab` 守住这条，
  另有 `test_frame_does_not_cover_any_cell_text` 逐格比对框线与文字的矩形是否相交。
- **竖线不能 `elide`。** 第一版把竖线当普通记号藏掉，想着「格子之间靠边框分隔」，
  但竖线是**唯一撑开列宽的东西**：藏了之后 `| 项目 | 数量 |` 渲染成 `项目数量`，
  各格文字挤成一团，表格直接散了。
  改成把竖线**染成很浅的边框色**充当列分隔线，文字位置一点不动；
  此时再画列分隔线会与它错位（列宽由字体决定，画布量不准），所以画布只画外框和行线。
  光标行上的竖线恢复成记号色，方便修改。
- **行分隔线会压到字上。** 按 `dline` 整行下沿画线，在行距为 0 时会贴着字形边框。
  改成算「上一行下沿」与「下一行上沿」之间的空隙，空隙放得下就把线画在正中，
  放不下才退到上沿之上。测试用了 2px 余量：紧贴边界不算遮挡，**穿过**字才算。
- **`_split_row` 反推位置不可靠。** 想用 `line.index(cell)` 找回每格在行内的位置，
  但格子前后都是空格，`index()` 会定位到空格而不是文字，首字就被吃掉。
  改成逐字符扫，另用 `_cell_spans()` 给出每格的准确区间给行内语法用。

## 2026-09-20 流畅度优化（专注模式切换 + 滚动）

用户反馈：切换专注模式和上下滑动时有卡顿。先量再改，全程用
`tools/_bench_smoothness.py`（动作 + 一整个事件循环）和 `tools/_bench_perf.py`
（单函数）对比，结论是**卡顿不在 Python 逻辑里，而在跨语言调用与窗口操作上**。

### 量出来的事实

- 一次 `_redraw_margins`（重画行号/徽标/装饰/表格框）里，`tk.call` 的耗时占九成以上；
  一次滚动重画要问 Tk 几百次「这是第几行」。
- `index("N.0 + 1 display lines")` 一次约 24 次 Tcl 调用，旧实现按**显示行**逐条推算，
  是滚动最贵的一步。
- `lift`（重排窗口）比普通 Tcl 调用贵两个数量级：一次重画给几十块画布各抬一次，
  光这一项就占整次重画的四成。
- **每移动一个 Tk 子窗口约 0.5 ms**（本机实测：1 块 0.71 ms、4 块 2.30 ms、12 块 6.44 ms；
  只改宽高不挪位置则只要 0.03 ms）。装饰用的是「一块装饰一块小画布」，
  滚动时十几块一起挪，这是现在滚动耗时的主要来源。

### 做了什么

1. **可见行只走一遍**：新增 `_visible_lines()`，返回
   `[(逻辑行号, 行内偏移, dlineinfo)]`；行号、徽标、装饰、表格框四个模块共用这一份结果。
   按**逻辑行**遍历（`dlineinfo("42.0")` 很便宜），只对引用和表格展开续行。
   以前四个模块各走一遍。
2. **解析结果缓存**：`_apply_markdown_styles` 顺带缓存 `_doc_blocks`、`_doc_in_code`、
   `_doc_tables`、`_heading_lines`、`_line_marks`、`_cursor_line`。
   滚动时 `_block_of()` 查表即可，不再重新 `get()` 行文本再 parse 一遍；
   徽标也不再逐行问 `tag_names()`。
3. **光标换行走轻量刷新**：`_refresh_cursor_line()` 只把「离开的那行」和「新到的那行」
   的记号在 `syntax` 与 `syntax_current` 之间互换（`_swap_cursor_marks`）。
   文本没变时整篇重解析纯属浪费，长文档下每敲一次键几十毫秒。
4. **几何缓存**：`_margin_state()`（留白 + 正文高度 + 视口起点）与上次绘制时记下的
   签名比对，一致就直接跳过重画。装饰画布与表格线画布各自也记 `decor_geometry` /
   `line_geometry`，没动过就不 `delete` + `create`。
5. **几何请求合并**：`_request_geometry()` 用 `after_idle` 把连续到来的 `<Configure>`
   合并成一次重排。
6. **留白同步生效**：`<Configure>` 里立刻算好 `padx`（`_sync_editor_padding`），
   不等空闲阶段。Tk 的重折行排在空闲阶段前头，晚一步就会**先按旧留白折一遍、
   再按新留白折一遍**，长文档白花几十毫秒。
7. **不再逐帧 `lift`**：徽标画布以前每帧把自己抬到最上面，逼得所有装饰画布也跟着逐帧抬。
   改成靠**创建顺序**（Tk 的兄弟窗口后建的在上）——新建画布时抬一次
   （`_raise_once`），之后一次都不抬。一次滚动少 15 次窗口重排。
8. **行内语法加廉价前置判断**：`_tag_inline` 先用 `"`"、"["、"**"` 等子串判断有没有
   对应的语法，没有就直接跳过整段正则。

### 效果（649 行文档，动作 + 一整个事件循环）

| 动作 | 优化前 | 优化后 |
| --- | --- | --- |
| 敲一个字（整篇重解析） | 54.3 ms | 20.7 ms |
| 移动光标一行（轻量刷新） | 54.3 ms | 6.3 ms |
| 滚动一格重画 | 33.8 ms | 3.0 ms |
| 切换专注模式 | 约 78 ms | 约 52 ms |

`_redraw_margins` 内部：装饰 2.70 → 0.43 ms、表格框 1.15 → 0.26 ms、
徽标定位 0.44 → 0.02 ms、整次重画 6.96 → 3.23 ms；`lift` 从 15 次/帧降到 0 次/帧。

### 踩到的坑

- **`_tkinter.tkapp.call` 是只读属性**，打不了补丁做调用计数。但每个控件的 `tk`
  是普通属性（`tkinter` 里就是 `self.tk = master.tk`），换成转发代理即可
  —— Tkinter 的每个方法最终都落到 `self.tk.call`。
- **判断「有没有白画一遍」要数改动型命令**（`delete`/`create`/`place`/`raise`），
  不能数全部 Tcl 调用：`index`/`dlineinfo` 是读，读多少次都不影响画面。
- **测试里的「移动」很容易写成空转**：位置只依赖循环下标时，第二圈起位置没变，
  `place` 变成空操作，量出来的耗时（0.03 ms）比真实值（6.44 ms）小两个数量级。
  基准脚本里必须让被测量的状态每次都真的变。
- **`yview_moveto` 在已经滚到底时是空操作**：视口起点不变，签名自然也不变，
  别拿它当「视口一定变了」的前提。
- **专注模式里装饰是**右**移的**：正文限宽居中，左栏藏起来后正文区域变宽，
  留白按比例变大，装饰跟着往右走。写测试时别想当然以为「变宽就左移」。
- **`end-1c` 的行号不是内容行数**：文件以换行结尾时 Tk 会多留一行空的收尾行，
  用 `re.split` 数行会把这一行也算进去。

### 已知取舍 / 还没做的

- **滚动时每帧仍要挪十几块装饰画布**，本机约 0.5 ms/块，合计约 15 ms/帧。
  这是「一块装饰一块小画布」这个设计的固有成本（Tk 的 Canvas 不透明，
  没法用一块大画布覆盖式绘制）。要再快一档，得把装饰改成**正文内嵌图片**
  （`text image_create`）——图片是正文自己的绘制内容，随文字一起滚动，
  一个窗口都不用挪。改动面较大，本轮没做。
- **敲字仍会整篇重解析**（4321 行时 67 ms/字）。光标移动已经走轻量路径，
  但文本一变就要重算全篇。要治本得做「增量重解析」：按行快照求出改动区间，
  从改动处重新解析到**状态重新收敛**为止，不收敛再退回整篇。
  这是目前剩下最大的一块。
- `_redraw_line_numbers` 每帧 `delete("all")` + 重建三十来个文字图元（约 1 ms）。
  换成复用图元反而要两次调用（`coords` + `itemconfigure`），不划算，保持现状。

## 2026-09-21 滚轮速度加倍 + 导出长图

需求原话：「增加鼠标滚动时编辑界面滑动的速度为现在的两倍；增加将全文输出成一张
图片的功能，宽度方便在手机上阅读，长度可以根据文章内容决定。」

### 滚轮：先量清楚「现在」是多少

不能凭印象。Tk 自带的 Text `<MouseWheel>` 绑定在本机是：

```tcl
if {%D >= 0} { %W yview scroll [expr {-%D/3}] pixels } \
else         { %W yview scroll [expr {(2-%D)/3}] pixels }
```

也就是**一格 40 像素**（不是「4 个单位」，单位是行，一单位≈22 px）。
所以「两倍」= 80 px，不是 8 个单位（那会是 4.4 倍）。

做法是照抄 Tk 的公式再乘系数，而不是「一格固定滚几行」：

```python
EDITOR_WHEEL_FACTOR = 2
pixels = delta / 3.0
self.editor.yview_scroll(int(round(-pixels * EDITOR_WHEEL_FACTOR)), "pixels")
return "break"      # 不拦住的话 Text 的类绑定会再滚一遍，变成三倍
```

按公式走的好处：高精度滚轮一个事件可能只有 40 而不是 120，不同滚轮、不同 DPI
下都正好翻倍。实测（`tools/_shot_export.py`）：

| 事件 | 系统默认 | 简记 | 倍数 |
| --- | ---: | ---: | ---: |
| delta = −120 | 39 px | 79 px | 2.03× |
| delta = +120 | 39 px | 79 px | 2.03× |
| delta = −240 | 79 px | 157 px | 1.99× |
| delta = +240 | 79 px | 157 px | 1.99× |

（±2 px 的零头来自 Tk 自己公式里 `(2-%D)/3` 的不对称取整。）

### 导出长图：为什么不用「开窗口截图」

窗口截图要靠 GDI 从窗口 DC 取像素：窗口被挡住、跑到屏幕外都拿到空白，
而且超长的窗口根本画不出来（还受屏幕高度限制）。所以改成**离屏渲染**：

1. `CreateDIBSection` 建一块 32 位**自上而下**的 DIB（`biHeight` 取负数）当画布；
2. `TextOutW` 画字、`FillRect` 铺底、`Ellipse`/`Rectangle`/`LineTo` 画标记与边框；
3. 自己写 PNG 编码（`zlib` + CRC），**逐行**读出位图边读边压。

全程不涉及任何窗口：不闪屏、不怕遮挡、想画多长画多长。

### 新增 `app/image_export.py`（只依赖标准库）

- **只管排版和画**，Markdown 解析与配色留在 `main.py`（那是它的知识）。
  调用方把文档整理成 `Row`（逻辑行）/ `Piece`（同样式片段）喂进来。
- 坐标、字号全部是**图片像素**；`main._export_options()` 按
  「正文目标字号 ÷ 编辑器字号」把界面上的逻辑尺寸整体放大，
  所以导出的图和屏幕上同比例，只是更宽更清楚。
- 配色由 `main.export_palette()` 从编辑器那套常量填进 `Palette`，
  两处不会各写一份而慢慢走偏。
- 块级判定直接复用 `parse_block` / `fence_step` / `build_table_rows`，
  行内样式复用同一套正则（`INLINE_CODE_RE` / `LINK_RE` / `EMPHASIS_PATTERNS`）。

### 排版上的三个关键决定

- **按基线对齐**：用 `GetTextMetricsW` 取 `tmAscent`/`tmDescent`，
  像 Tk 一样把「行高 − 字体自然行高」的差额分成两半（段首一半、段尾一半），
  基线落在 `段首留白 + ascent`。中英文混排、等宽/比例字体混排都不会高低不齐。
- **一张表一个 `Row`**：列宽必须整张表一起算，否则各行各算各的，列对不齐。
- **分张只切在行边界**，而且**绝不切开一张表**（同一张表的行共享同一个 `Row`
  对象，切分时看到 `current[-1].row is line.row` 就不切）。

### 踩到的坑（都很值钱）

1. **`FillRect` 在 user32，不在 gdi32。** 报 `function 'FillRect' not found`
   才发现——它一直挂在 gdi32 上是想当然。
2. **`_shift_chunk` 只挪了 `top` 没挪 `baseline`。** 底色、边框、引用竖条都
   按 `top` 画，文字按 `baseline` 画，于是「框走了字没走」，整页文字叠在顶上。
   教训：凡是同一份坐标有两处消费者，挪动时一定要一起挪。
3. **行内记号必须真的从文字里剔掉。** 编辑器靠 `elide` 藏 `**`、`` ` ``、`[`、`](url)`，
   图里没有 elide 这回事。第一版只把「有样式的那一段」记下来，
   记号就原样画了出来——图上明晃晃写着 Markdown 源码。
   改法：`_inline_spans` 同时返回「要丢掉的记号区间」。
4. **代码块里不能跑行内解析。** `_export_pieces` 对代码行也跑了一遍，
   于是 ``` ```markdown ``` 块里的 `*x*`、`~~x~~` 被当语法处理、记号被吃掉。
   编辑器对这些行只套 `codeblock` 标签，图里也必须原样输出。
5. **断在空格后时忘了把 `index` 退回去。** 断点之后的字「走过」了但没算进新行，
   新行于是悄悄超宽——画出来就是右边被切掉（`使用说明` 里 5 行中招）。
   改法：`start = index = cut` 重新累加。
6. **PNG 少了 IDAT 外壳。** 重构成「边读边压」时把压好的数据直接拼进了字节流，
   忘了包 `length + tag + data + CRC`。文件头看着还是 PNG，看图工具也宽容地认了，
   是裁切工具按分块结构走一遍才炸出来。现在有 `png_chunks()` 专门守这条：
   逐块校验 CRC，并确认 IDAT 解出来正好是 `height × (行字节 + 1)`。
7. **64 位句柄不声明 `argtypes` 会偶发崩溃。** `GetDC` 返回的句柄超过 2^31 时，
   ctypes 按 C 的 `int` 传参会抛 `OverflowError: int too long to convert`。
   这个隐患在 `main.enable_dpi_awareness()` 和 `tools/capture_window.py` 里都有，
   平时句柄小就碰不到，这次恰好撞上——**必须显式声明，不能靠运气**。
8. **量滚轮必须用长文档、且从正确的一端开始量。** 文档比视口短时根本没得滚；
   「向下滚」要先顶到最上面、「向上滚」要先顶到最下面，否则量出来是 0。

## 2026-09-21 增量重解析（长文敲字不再卡）

### 问题

`_on_editor_modified` 以前每次都调 `_apply_markdown_styles()`，那是**整篇**重解析：
读全文 → 切行 → 扫围栏/表格 → 给每一行套样式。文档越长越贵，且与改动大小无关。

先量了一下（4341 行）：

```
整篇重解析中位数 79.6 ms
其中编辑器发出的 Tcl 调用 9183 次，合计 47.2 ms   → Tcl 占 59%，Python 侧 41%
  调用最多的 Tcl 子命令：
    tag                     9100 次   34.2 ms
    .!frame3.!frame2.!text    67 次   13.0 ms
```

结论：贵的是 **Tcl 的 `tag_*` 调用**（9100 次里绝大多数是逐行的 `tag_add`/`tag_remove`），
不是 Python 正则。而 `tag` 调用次数与**行数**成正比——所以只要「不碰没变过的行」，
成本就能降一个量级。这也解释了为什么优化方向是增量，而不是把正则写快一点。

### 做法

新增 `_apply_markdown_styles_incremental()`，打字时先走它，返回 `False` 才退回整篇。

**1. 找改动区**（`_changed_region`）。只读光标上下各 48 行（`INCREMENTAL_WINDOW`），
在这段窗口里比对：

- 改动点**之前**的行：同下标应当相同 → 取最长相同前缀。
- 改动点**之后**的行：错开 `delta = 新行数 − 旧行数` 应当相同 → 取最长相同后缀。

两边夹出来的就是改动区。不需要知道 Tk 内部是怎么改的，插入、删除、跨行删除
都能一次算准。窗口里完全对得上（说明改动落在窗口外）就返回 `None` 退回整篇。

**2. 校验区外没被波及**（`_region_context`）。围栏和表格都是跨行语法，只算区里不够：

- 算完改动区，把「区末之后的围栏状态」和改动前比一下。不一致就说明后面每一行的
  「是否代码块」都变了 → 整篇重算。
- 表格：改动行里没有 `|`、附近也没有缓存表格时直接跳过（正文打字走这条快路，
  这是绝大多数情况）。沾到边就多读 ±64 行（`TABLE_LOOKAROUND`）重扫，并确认
  「改动区落在哪张表里、表的起止行」都没变。

**3. 只重刷改动区**（`_clear_line_tags` + `_style_line`）。关键认知：
**Tk 会自己把插入点之后的标签跟着文本一起挪**，所以区外的行根本不用重新上色，
只要把按行号索引的那几份缓存对齐过去就行。抹标签按「一个标签一次整段 range」
清（26 个标签 = 26 次 Tcl 调用，与区间长度无关），绝不逐行清。

**4. 两条路径共用一份上色逻辑**（`_style_line`）。整篇和增量如果各写一遍，
迟早会在某个语法上不一致——屏幕上和导出图不一致的 bug 就是这么来的。

### 踩到的坑（三条都是真的）

**① 行模型：`\r` 不是换行。** Tk 的 Text 以 `\n` 分行，行尾那个 `\r` 是**行内容**
（`get("3.0","3.end")` 会把它带回来）。原来三处都在用
`re.split(r"\r\n|\r|\n", text)`，遇到**单独**的 `\r` 就多切一行：

```
index("end-1c") = 32 行     \r\n 出现 29 次     单独 \r 出现 1 次
re.split(r"\r\n|\r|\n") → 33 行     按 "\n" 切 → 32 行
```

于是行号整体错位，比对全挂。新增 `split_document_lines()` 统一处理，
**也不能用 `str.splitlines()`**（它还会在 `\x0b`、U+2028 处断开）。
另外 **空行的 `end` 就是它的起点**，`get()` 一个字符都不返回，读回来要补齐长度。

**② 光标行的标签名不会跟着改。** Tk 把标签跟着文本挪，但**不改名**。
光标行原来叫 `syntax_current`，光标挪走之后那一行还叫 `syntax_current`，
而新的光标行拿到的是 `syntax`——两边都错。只补「离开的那一行」不够，
重刷范围必须**同时包含新光标行和旧光标行**（`first/last` 各取一次 `min`/`max`）。

**③ 位移顺序。** 正确顺序是：
`_drop_line_marks`（按**旧**行号清改动区的记录）→ `_shift_line_maps`（按 delta 挪区外的记录）
→ 抹标签 → 重新上色。反过来做的话，刚给改动区填进去的新记录会被
「挪改动区之后的记录」这一步**再挪一次**（表现为记号行号错位、H1 徽标消失）。

### 验证证据

- `python tools/run_tests.py` → **350 个测试全过**（新增 `tests/test_incremental.py` 12 个）。
- `tools/_check_incremental.py` → **「共 22 项：不一致 0 项，其中退回整篇 5 项」**。
  22 种改动逐一「先走增量、再整篇重解析，逐项比对」。
- `tools/_bench_perf.py 140`（4341 行）→ **敲一个字 73.2 ms → 3.1 ms（23.6×）**；
  `tools/_bench_perf.py`（1241 行）→ 21.5 → 2.7 ms（7.9×）。
- 实测 tag 调用次数：普通正文里敲一个字，**增量 15 次 / 整篇 780 次（省 98%）**。
- 11 种常见改动全部走增量：插字、行尾接着打字、中间换行、行首敲 `#`/`>`/`-`、
  列表缩进、表格数据行插字、代码块插字、标题行插字。

新增的 12 个测试守三条：**增量结果必须与整篇逐项一致**（标签区间、块类型、
围栏状态、表格范围、记号区间、标题徽标）、**行模型必须和控件一致**
（`len(_doc_lines) == index("end-1c")` 的行号）、**增量真的只动改动区**
（数 `tag` 调用次数，远低于整篇才算数——不然哪天悄悄退化成整篇，性能测试也未必看得出来）。

写测试时自己踩的两个坑（**实现是对的，是测试写错了**）：

- 比对前必须调 `_refresh_cursor_line()` 再挪光标。真实使用中光标是靠方向键/鼠标挪的，
  那时应用会走「光标换行轻量刷新」；不补这一步，比出来的差异全是假的。
- 用 `insert` 造改动时别让 Tk 把选区丢掉。有两例（在较短行上写、`insert` 后跟
  `root.update()`）因为选区跨行、控件不持有它而被静默丢弃，改动根本没发生。
  改成「行尾打字」「写到行尾之外」这类真实动作。

### 已知取舍

- **宁可慢一次，不能算错。** 围栏开合、表格结构变化、一次粘太多行、改动和光标离得
  太远（超过 4 × 窗口）时一律退回整篇。这些都不是打字热路径，退回整篇的代价可以接受。
- **表格改动偏保守**：只要沾到表格就重扫 ±64 行。实测表格**数据行**里插字仍走增量，
  往**分隔行**里插字会退回整篇——那确实会把表破坏掉，退回是对的。
- 增量还剩一点可省：`_tag_inline` 占整篇重解析 21.7 ms / 81 ms（Python 正则 +
  它自己发出的 Tcl 调用），把同一标签的多个区间合并成一次 `tag_add` 有望再砍一截。
  但整篇现在只在「打开文件」和「改动动了围栏/表格」时跑，收益只体现在打开长文档的速度上。

## 2026-09-21 修复「中间列表滚一下，顶部空出一条」的空白

### 问题

用户报「预览栏下拉出现空白」，澄清后是**中间文稿列表**：滚到最顶部时，
标题「全部文稿」和第一张卡片之间空出一条（截图里约 107 逻辑像素），
第一张卡片被整个推下去，滚动条看上去却完全正常。

### 排查（先走了三条弯路，都记下来免得重走）

1. **拿用户的真实文件夹 + 真实设置反复滚动**：滚到顶/底、滚轮超滚、窗口改高改矮、
   切换专注模式、切子文件夹再切回来 —— 每次最靠上的卡片都在同一个位置，**复现不出来**。
2. **怀疑是卡片高度量错或滚动区算错**：验证 `bbox()` 对视口外的图元照样有效、
   Tk 会把越界的 `yview` 自动夹回，都不是。
3. **逐像素量用户的截图**才定下坐标：红框内（y 71–242）是**纯背景**，
   连白卡片和边框都没有；卡片间距 18px、标题 10pt 字高 20px，
   反推出显示缩放 **150%**，于是「空白 ≈ 107 逻辑像素」这个数才可用。

### 真正的原因：Tk 的 Canvas 只在「滚动区比视口高」时才夹原点

`Canvas` 的原点越界与否，**取决于滚动区高度和视口高度的比较**（实测矩阵）：

| 情况 | `yview_scroll(-1, "units")` 之后 |
| --- | --- |
| 内容比视口高（1000 > 400） | 原点停在 0，正常夹住 |
| 内容比视口矮（110 < 400） | 原点变成 **−40**，再滚一格 −80；`yview()` 仍报 `(0.0, 1.0)` |

也就是说：**文档少到一屏放得下时，往上滚会把整列内容推到下方**，
顶上留出「一格 = 视口高 ÷ 10」的空白，而 `yview()` 谎报在顶部、
滚动条是满格的长滑块 —— 界面上看不出任何异常，只能靠往回滚才恢复。
用户截图里那 107 像素，正好是 1067 高的画布滚了一格（1067 ÷ 10 ≈ 107）。

同一件事在别的控件上**不会**发生（都实测过）：`ttk.Treeview` 与 `tk.Text`
的 `yview_scroll` 自己就夹得住，所以左侧文件夹树和右侧编辑区没问题。
只有中间那个 `Canvas` 会中招。

### 修复（`app/main.py`）

- 新增 `_clamp_cards_scroll()`：`canvasy(0) < 0` 就把原点夹回 0。
- 滚轮、滚动条命令各接一次（`_on_cards_scrollbar` 转发后也夹一次）。
- 抽出 `_set_cards_scrollregion()`：重建时设置滚动区后顺手夹一次，
  清掉任何残留的负原点（重建本身不会重置原点，滚动区没变时 Tk 不发事件）。

### 验证证据

- 新增 `tests/test_cards.py::CardScrollBoundsTests` 5 项：往上滚一格不推、
  连滚 5 格不累积留白、滚动条命令不推、重建能清掉越界原点、
  **长列表仍能正常滚**（防止夹过头）。
- `tools/_check_clamp_guard.py`：把 `_clamp_cards_scroll` 换成空函数再跑这 5 项，
  **4 项失败**（`canvasy(0) = -105.0`，正好一格），证明测试真抓得住这个 bug。
- `tools/_shot_cards_scroll_blank.py`：真实应用里复现并出图
  `outputs/修复前-顶部空白.png`（顶部一条空白、卡片被推下去）与
  `outputs/修复后-顶部无空白.png`（卡片贴顶）。
- 全量测试 **355 项全过**（338 → 350 → 355）。

### 已知取舍

- 夹原点用的是「每次滚轮事件后读一次 `canvasy(0)`」，多一次 Tcl 调用；
  滚轮是用户节奏的事件，这点开销无所谓。
- 只在滚动区**装得下**时才会出现负原点，所以夹的判据就是 `canvasy(0) < 0`，
  不需要另外判断内容高低，也不会影响正常滚动。

## 2026-09-22 把文档移动到指定文件夹

用户要求「加入可移动文档到指定文件夹功能」。

### 问题

此前文档只能待在**新建时所在的那个文件夹**里。文稿列是按文件夹筛选的（点树上的
节点筛选中间列表），所以一篇文档一旦建错地方，唯一的办法是去资源管理器里手动拖——
而这恰恰违背了「软件只是读写这些文件的壳」的定位：壳该把常见操作做掉。

### 做法

分两层，文件系统那一层在 `app/storage.py`，界面那一层在 `app/main.py`。

**`app/storage.py`**（新原语，跟 `create_folder`/`delete_document` 放一起）：

- `unique_path(directory, name)`：找一个不冲突的文件名，`a.md → a-2.md → a-3.md…`。
- `_ensure_inside(path, root, message)`：确认路径在 root 内，否则抛 `OSError`。
- `move_to_folder(path, target_dir, root) -> Path`：把文档移到 `target_dir` 下，返回新路径。
  **绝不覆盖**同名文件（走 `unique_path` 加序号）；源文档与目标文件夹**都必须在 root 内**
  ——界面本来就只列 root 下的子文件夹，这里再拦一道，免得哪天界面出 bug 把文件挪出日记文件夹；
  目标就是当前文件夹时**原样返回**，调用方据此判断「没动」。
  用 `os.replace`（同盘符下是改目录项，不是复制粘贴，快且原子）。

**`app/main.py`**：

- `_doc_menu()` 里加一项 `移动到` 级联菜单。子菜单内容是 `_move_targets()`：
  **跳过文档当前所在的文件夹**（移过去等于没动），根目录显示成「全部文稿（根目录）」，
  子文件夹显示相对路径（`读书/书摘`）。一个可选项都没有时，放一条灰掉的「没有其他文件夹」，
  菜单不至于空着。子菜单末尾是 `新建文件夹并移动…`。
- `_folder_label(path)`：文件夹的显示名，根目录 → 「全部文稿」，其余 → 相对路径。
  状态栏「已移动到：X」用它。
- `move_document_to(path, target)`：当前文档是脏的**先存一次**（否则移完编辑器还指着旧路径，
  下次自动保存会**把文件在原地又写回来**）；调 `move_to_folder`；移的正是打开着的那篇时
  把 `self.current_path` 跟着更新，然后 `refresh_files()`，状态栏报去向。
  失败（目标不存在、越界、文件没了）弹错误框，**文件留在原地**。
- `new_folder_and_move(path)`：问名字 → 建在「全部文稿」下 → 重建树 → 再走 `move_document_to`。
  重名不报错，改成提示「已存在，可直接移动到它」。
- `_ask_folder_name(title, prompt)`：取消 / 空白 / 含 `\ / : * ? " < > |` 都返回 `None`
  （含非法字符时弹一次错误）。`new_subfolder` 也改成复用它，两处的校验规则从此只有一份。

### 验证证据

- `tests/test_move_document.py`（**23 项，全绿**），分两组：
  - `MoveToFolderTests`（storage 层 10 项）：移动后内容不变、同文件夹是空操作、
    **不覆盖**同名（`a.md` → `a-2.md`）、再撞就是 `a-3.md`、`unique_path` 后缀处理、
    拒绝 root 之外的源、拒绝 root 之外的目标、目标文件夹不存在、源文件不存在。
  - `MoveDocumentUiTests`（界面层 13 项）：菜单里有级联项与删除项、子菜单列出的文件夹带相对路径、
    跳过当前所在文件夹、**不列回收站**、移动当前文档后仍然打开着、移动后还能继续保存、
    移动别的文档不影响当前文档、移走的文档从当前筛选列表里消失、重名会改名并在状态栏报出来、
    失败时弹错误且文件还在、新建文件夹并移动、取消不改动任何东西、非法名字被拒。
- 菜单文案程序化核对：
  主菜单 `['打开', '在资源管理器中显示', '移动到', '删除文档（移到回收站）']`；
  子菜单 `['工作', '生活', '读书', '读书/书摘', '新建文件夹并移动…']`。
- `outputs/移动到-右键菜单.png`、`outputs/移动到-子菜单.png`（人工核验用）。

### 顺手解决的一个卡点：Windows 上截不到弹出菜单

`outputs/移动到-右键菜单.png` 一开始总是 1×1 —— Tk 的菜单是**原生菜单**，`winfo_id()`
拿到的是个没有客户区的壳。改成从屏幕 DC 截（`tools/capture_window.py` 新增
`grab_screen_rect` / `capture_screen_rect`）之后尺寸对了，但脚本**直接挂死**。

定位（`tools/_probe_menu_post.py`，逐段打标记）显示最后一个标记停在 `before post`：
**Windows 上 `menu.post()` 本身就不返回**——Tk 走的是原生 `TrackPopupMenu`，
那是个模态循环，菜单不被点掉就一直在里面（`tk_popup` 同理，而且它还会抢输入）。
所以「先 post、再截图」的顺序根本走不通，主线程一进 post 就再也回不来。

修法是把顺序倒过来：**先起一个后台线程**，睡 1.2 秒等菜单画出来，再抓屏幕写 PNG，
最后 `os._exit(0)` 收摊。抓屏走的是纯 ctypes 的 GDI（`capture_screen_rect`，完全不碰 Tk），
所以主线程正卡在模态循环里也不影响子线程。见 `tools/_shot_doc_menu.py`（当时叫 `_shot_move_menu.py`，后改名）。

因为一个进程只能摆一个菜单（摆了就出不来），主菜单和子菜单是**跑两次**分别截的，
加参数区分：`python tools/_shot_doc_menu.py [sub]`。

### 已知取舍

- 目标只列**当前日记文件夹内**的文件夹，不能移到文件夹外——故意的，避免手滑把日记挪到
  云盘同步范围之外。`move_to_folder` 里的 `_ensure_inside` 是第二道锁。
- 「新建文件夹并移动」只能建在**根目录**下（不支持建到某个子文件夹里）。要做也能做，
  只是对话框得从「输名字」变成「选位置 + 输名字」，眼下用不到。
- 移动**没有撤销**。但因为是同盘改目录项，且重名会自动改名、绝不覆盖，最坏情况是文件换个
  位置而不是丢内容。
- 移走文档后**不自动把筛选切到目标文件夹**（列表里它会消失，状态栏会报去哪了）。
  留在原地的好处是「一次移动不会把视线拽走」；若用户觉得别扭，可以改成跟随。
- 没有拖拽移动（Drag & Drop）。Tk 里做跨控件拖放成本不低，菜单已经够用。

### 测试

全量 **378 项 OK**（移动功能之前是 355 项，本轮新增 23 项）。

第一次跑全量时抓到 **两条** 问题。都跟本功能无关，但都是「上一轮按用户要求没跑全量」
欠下的账：

1. **一条过期断言**（真失败）：`tests/test_export.py` 里
   `test_wheel_scrolls_exactly_twice_the_system_default` 把滚轮倍数**写死成 2.0**，
   滚轮改成 6 倍后必然失败（实测 5.975）。改成断言直接取 `app_main.EDITOR_WHEEL_FACTOR`
   并改名 `test_wheel_scrolls_exactly_the_configured_factor`，以后再调倍数不用动测试。
   **教训：常量型断言别写死数字。**
2. **一条偶发失败**（`test_performance` 抛 `StopIteration`）：第二次跑全量时
   `test_wrapped_quote_gets_continuation_lines` 挂了，第一次却是好的，单独跑 3 次全过。
   根因是 `_visible_lines()` 按 `editor.winfo_height()` 算可见范围（`max(1, height)`），
   而窗口刚映射时高度可能还是 **1** —— 那就只看得到第 1 行，第 4 行那条引用自然找不到。
   单独跑这个模块时窗口映射得快，全量跑时负载一高就偶发。修法是在 `setUp` 里等编辑区
   拿到真实高度（最多约 1 秒，等不到就明确报出来），并把裸 `next()` 换成带
   「可见行 / 视口 / 编辑区高 / 第 4 行内容」的断言消息，免得下次只得到一个没有信息的
   `StopIteration`。
   **这不是应用 bug**：真人用的时候窗口早就映射好了，是测试夹具对环境过于敏感。

修完连跑两次全量，**378 项全绿**。

## 2026-09-22 界面外壳一轮：导出入口、顶部栏、序号、编辑状态

用户一次提了六件事。前四件是「把已有的东西挪到更顺手的地方」，后两件是「让界面安静下来」。

### 1. 「导出长图」从顶栏挪到文稿右键菜单

顶栏不再有导出按钮，右键菜单里多一项 `导出长图`，位置在「在资源管理器中显示」之后。

关键是**右键哪一篇就导出哪一篇**，不必先打开它。所以 `export_long_image(path=None)`
多了个参数，正文来源分两种（`_export_source`）：正好是当前打开的那篇时用编辑区的文本
（把还没自动保存的改动也算上），否则 `read_markdown` 从磁盘读。默认文件名也跟着那篇走
（`_export_default_path(path)`）。`path=None` 仍然表示「当前文档」，老调用方不用改。

### 2. 导出完自动打开所在文件夹

写完盘调 `_reveal(written[0])`，复用「在资源管理器中显示」那条路
（`explorer /select,` 会打开文件夹并选中刚导出的那张）。取消保存、导出失败都不打开。

### 3. 拼音字母预览的字号跟正文一致

输入法的组字（拼音预览）字号归 Windows 的输入法管，默认是输入法自己那一套，和正文对不上；
Tk 也不会把控件字体同步过去（Tcl 层根本没有相关命令，查过 `info commands *ime*` 只有 `time`）。
所以只能自己调 imm32：`ImmGetContext` → `ImmSetCompositionFontW` → `ImmReleaseContext`，
`lfHeight` 取 `-px(font_size)`（负数 = 字符高度，单位像素），字族取当前正文字体。
在 `_apply_typography`（改字号/字体时）和编辑区 `<FocusIn>`（组字字体挂在窗口上）各设一次。

「该用哪个字体」是纯计算，单独抽成 `_ime_logfont()` 以便测试——真去调 Windows 那一步
在测试里造不出来，但算错字号必须能被发现。整段包 try/except：拿不到输入法上下文就安静过去，
绝不能因为这事打断打字。

### 4. 有序列表的序号：一律蓝色、与正文同号

原来序号是**画布画的 11px 蓝色小字**，而光标一移进那一行，记号不再 elide、露出灰色源码
（`SYNTAX_COLOR`），序号于是在「蓝色小字」和「灰色大字」之间跳。

改成序号**永远**由画布绘制：

- `_style_line` 里有序列表的记号直接 `tag_add("syntax", ...)`，**不走 `_tag_syntax`**
  ——不记进 `_line_marks`，光标进出就不会去互换它，永远保持 elide。
- `_decoration_spec` 里把有序列表排除在「光标行不画装饰」之外。
- `_draw_decoration` 里字号从写死的 `px(11)` 改成 `px(settings["font_size"])`，
  画布宽度也跟着字号走（`max(px(34), 字号*2)`），免得字号调大后序号被裁掉。

项目符号/复选框**维持原样**（光标行露源码、不画符号），专门留了一条测试钉住这个对比，
防止哪天把「有序列表的例外」顺手扩大化。

### 5. 顶部栏自动隐藏，鼠标扫过再出来

顶部栏（左侧编辑状态 + 右侧「专注模式」）平时收起，鼠标进到编辑区顶部
`px(TOP_BAR_HEIGHT)` 那条窄带里就滑出来，离开 `TOP_BAR_HIDE_DELAY`(700ms) 再收起。
「专注模式」本来就在这条栏里，收起/滑出时跟着一起走。

三个实现要点：

- **用 `grid_remove()`/`grid()`，不手动改高度。** 收起只动**高度**不动**宽度**，
  所以正文不会重新折行。宽度一变 Tk 要把整篇重排一遍（长文档几十毫秒），
  跟着鼠标进出跑会非常明显。有一条测试专门钉这个不变量。
- **`<Motion>` 绑在 toplevel 上**（子控件的鼠标动作会经 bindtags 冒泡上来），
  所以它能收到整个窗口的移动。这个回调触发极频繁，里面只做几次整数比较，
  真正动 Tk 的只有「该显示/该收起」翻转那一次；编辑区在屏幕上的位置缓存起来
  （`_panel_rect`），窗口 `<Configure>` 时失效重取。
- **有迟滞、有延时。** 移开只是排期（`after`），回到窄带里就取消排期。
  收起后不会来回抖：窄带的位置不随顶部栏显隐变化，所以不会出现「收起→鼠标落在窄带里→又弹出」。

顺带把 `topbar_hide_job` 加进 `_cancel_after_jobs`——不然窗口销毁时回调会在解释器拆掉后触发。

### 6. 编辑状态：编辑中「…」，存完不显示

`正在编辑…` → `…`，`已保存` → 空字符串。只改这两处，其它临时提示
（已移动到、已导出长图、导出失败…）照旧。

### 验证证据

- 新增 `tests/test_editor_chrome.py`（**17 项**）：顶部栏 10 项（初始可见、移开只排期不立刻收、

  编辑状态 3 项、输入法 4 项（字体与正文同号、改字号跟着变、排版变化会重设、调用不抛异常）。

- `tests/test_markdown_syntax.py`：新增 4 项（序号字号=正文字号且为蓝色、光标移进该行序号仍在、

  `outputs/有序列表序号-光标在该行.png`、`outputs/有序列表序号-光标不在该行.png`、

### 顺手修的：菜单截图脚本会偶发截不到

`tools/_shot_move_menu.py` 改名为 `tools/_shot_doc_menu.py`（菜单里现在不止「移动到」）。
改名后跑，**偶发截不到图**：`post()` 会阻塞，但**窗口还没真正映射出来时它可能立刻返回**，
于是 `main()` 返回、进程结束，daemon 抓屏线程被直接掐掉，图就没了。
两处加固：等窗口 `winfo_viewable()` 再摆菜单；摆完不假设 `post` 一定阻塞，
而是 `done.wait(15)` 等抓屏线程收工。连跑两轮 4 张图都稳。

### 已知取舍

- 顶部栏收起后，左侧的编辑状态也就看不见了——要看就得把鼠标移上去。这是「整屏留给正文」
  必然的代价；如果更想要「状态一直可见」，可以改成只在专注模式下自动隐藏。
- 有序列表的记号永远 elide，所以**光标停在该行时也看不到 `1.` 本身**，
  想改 `1.` 和 `1)` 的区别得先把它删了重打。这是用户要的「无论光标在哪都一样」的直接后果。
- 导出后自动打开资源管理器是**无条件**的，没做成设置项。
- 输入法组字那一段依赖 `imm32` 的窗口上下文，测试里造不出来，只验证了「算出来的字体对不对」
  与「调用不炸」；真实观感需要用户打字确认。

## 2026-09-23 撤回顶部栏自动隐藏，并修掉三个 bug

用户逐条反馈了四件事，其中第 1 件是撤回上一轮的改动：

> 1. 撤回这条更新，复原为上一版：自动隐藏顶部标题栏……将专注模式集中到顶部标题栏。
> 2. 有序标号换行后，标号会显示不全。
> 3. 点击文稿预览框时会随机滚动。
> 4. 编辑时左上角未显示"…"。
> 5. 鼠标点击预览栏，有时会选不中文档。

### 1. 撤回顶部栏自动隐藏

顶部栏退回**常显**，专注模式仍在右上角。

收起的本意是「把整屏留给正文」，但代价是：**收起时左上角的编辑状态也跟着没了**。
而「正在编辑」恰恰是打字时最想看到的反馈——用户报的第 4 条（编辑时左上角未显示「…」）
就是这件事的表象，不是状态逻辑写错了。

撤回时把整套机制连状态一起删掉，不留残骸：

- `root` 上的 `<Motion>` / `<Configure>` 绑定，`editor_panel` 上的 `<Configure>` 绑定；
- `_on_pointer_motion`、`_topbar_zone`、`_panel_geometry`、`_on_window_geometry_changed`、
  `_schedule_topbar_hide`、`_cancel_topbar_hide`、`_hide_topbar`、`_set_topbar_visible`；
- `TOP_BAR_HIDE_DELAY` 常量，`topbar_visible` / `topbar_hide_job` / `_panel_rect` 状态，
  以及 `_cancel_after_jobs` 里的 `topbar_hide_job`。

留着的坏处很实在：`tests/test_editor_chrome.py` 里专门有一条测试断言这些名字**都不存在**——
代码里还剩半个机制，下次读代码的人就会以为这个功能还在。

顶部栏本身保留 `grid_propagate(False)` + 固定高度，状态文字长短都不会让整条栏跳动。

### 2. 折行的有序序号被裁掉大半（真 bug，Tk 的坑）

**现象**：有序项一旦折行，序号只剩底下一点（见 `outputs/修复前-序号折行被裁.png`，
`2.` 和 `4.` 只剩一个小点）。不折行的序号完全正常。折行的引用，第一段竖条也缩成一小截。

**定位**：先量出折行那一行的 `dlineinfo`：

```
行3  1. 短的一条      dline=(237, 115, 122, 33, 25)     ← 正常
行4  2. 很长的……（折行）dline=(237, 148,   0,  2,  1)     ← 空盒子！
行5  3. 第三条        dline=(237, 283,  99, 33, 25)     ← 正常
```

再逐列量同一行：

```
4.0 -> (237, 148, 0, 2, 1)      空
4.1 -> (237, 148, 0, 2, 1)      空
4.3 -> (267, 150, 437, 33, 26)  好   ← 记号 `2. ` 到 4.3 结束
```

**原因**：Tk 对**自动换行的显示行**是按该行**第一个 chunk** 算几何的。行首那段一旦被
elide（`1. `、`- `、`> `、`# ` 平时都藏着），返回的就是 `(x, y, 0, 2, 1)`——宽 0、高 2、
基线 1。不折行的行 Tk 给的是整个显示行的盒子，所以只有「折行 + 行首 elide」这个组合会中招。

于是序号画布的几何算成：

```
height = max(px(16), 2) = 24        ← 比字还矮
centre_y = (148 + 1) - px(15)*0.36  ← 基线用了那个 1
文字 y（画布内）= centre_y - 148 = -7.3   ← 跑到画布外面去了
```

只有字的下沿那 4px 落在画布内，所以看到的是「只剩一点」。

**修复**：新增 `_display_line_box(index)`，统一量显示行：

1. 先按老办法量 `dlineinfo(index)`；盒子是真的（`is_real_display_box`）就直接用。
2. 盒子是行首那个 elided chunk 的盒子（宽 0），说明行首那段被 elide 了——用
   `index + 1 display chars` 重新量。**`display chars` 会跳过 elide 的字符**，
   一次就落到第一个真正显示出来的字上，与缩进多少列无关。
3. 量到的盒子**直接就用**，不要和那个空盒子合并：空盒子的 `y` 比真上沿还**高**
   一个行距（见下面补记）。

> 这一版之前还用过「盒子高度 `>= MIN_DISPLAY_LINE_H`（= 6）」当判据，**已经删掉**：
> 空盒子的高度是「行高 − 字体行距」，会跟着用户的**行高设置**变——默认行高 22 时
> 只有 2 像素，把行高调到 34 就是 16 像素，绝对阈值整个漏掉。判据改成看**宽度**
> （`box[2] > 0`）加**相对高度**（`box[3] >= px(line_height)`），与字号行高都无关。

`_visible_lines` 和 `_continuation_lines` 都改走它，所以折行的引用竖条一起修好了
（第一段从 12px 变成 35px，与后面几段连成一条）。

#### 补记：第一版修复不够，缩进深了就复发

第一版写的是「往后**逐列**试，最多 8 列」（`MAX_ELIDED_PREFIX = 8`），依据是「elide 的
记号最长是任务项的 `- [ ] ` 六列」。这个依据**是错的**——有序项的记号带着缩进一起被
elide，缩进四级就是 11 列：

```
     1.   → 第 7 列            ✓ 在 8 列以内
       1.   → 第 9 列            ✗ 超上限
         1.   → 第 11 列         ✗ 超上限
```

超了上限就退回空盒子，序号照旧被裁。用户反馈「序号折行之后还是会有标号显示不全」就是
这一种。摆出 12 种形态一次量出来的结果：

| 形态 | 第一版 | 现在 |
| --- | --- | --- |
| `1. ` / `2) ` / `10. ` / `100. ` + 长文 | 好 | 好 |
| `  1. `（二级）/ `    1. `（三级） | 好 | 好 |
| `      1. `（四级，9 列） | **裁** | 好 |
| `        1. `（五级，11 列） | **裁** | 好 |
| 任务项 `- [ ] `、引用 `> `、标题 `# ` | 好 | 好 |

改成 `+ 1 display chars` 之后**不依赖记号有多长**，一次调用就到位（实测：3 列、9 列、
11 列的行首前缀都准确落在第一个显示字符上），比逐列试还便宜。所以
`MAX_ELIDED_PREFIX` 这个常量直接删掉了——留着就是留一个「多长算够长」的假设，
而这个假设正是第一版翻车的地方。

**教训**：定「上限」的时候，得先量清楚上界到底在哪，而不是照着当下最常见的几种形态
估一个。另外这个 bug 说明**样例要覆盖到极端**——四级、五级缩进在样例里没有，
所以第一版测试全绿，用户一用就露。

### 3. 点击文稿卡片：选不中、还乱跳（两个独立的 bug）

列表没滚动时两者恰好一样，一滚动就差一个原点。量出来的结果：

```
滚到中间（原点 1668）：前 12 张点不中，后 12 张全选错（第 12 张 -> 第 0 张）

- 圆角（过去是拿图元撞，圆角处撞不到）。

横向干脆不参与判定：这一列里除了卡片就是留白，点哪儿都是想选那一张。

**3b 乱跳**——`_scroll_cards_to_current` 写的是 `yview_moveto(index / total - 0.15)`，

### 1. 序号折行被裁——**终于找到真因：判据用了一个绝对高度阈值**

前两轮修复都以为修好了，因为**探针自己就量错了**：所有探针都把 `state.json` 指到
临时文件，于是读的是 `DEFAULT_SETTINGS`（`line_width 50 / font_size 15 / line_height 22`
→ 字号 23px、行高 33px），而用户实际是 `60 / 18 / 34` → **字号 27px、行高 51px**，
正文列宽也不同，折行位置完全不一样。**修复在一个用户根本看不到的排版下验证的。**

把用户真实设置喂进临时 `state.json` 再量，真因立刻现形：

**空盒子的高度 = `px(行高) − 字体行距`**，也就是行距那一截——默认设置下只有 2 像素，
行高调到 34 就是 **16 像素**。而判据写的是「高度 < `MIN_DISPLAY_LINE_H`（= 6）就当空盒子」，
16 > 6，于是那个坏盒子被当成好盒子照用，序号照旧被裁。**绝对高度阈值一定会漏。**

三条实测事实（同一条折行有序项，`2.` 的记号被 elide）：

```
默认（字号 23px、行高 22 → 33px，extra = 2）
  dlineinfo("2.0")  = (237,  33,   0,  2,  1)   ← 空盒子
  dlineinfo("2.4")  = (267,  35, 437, 33, 26)   好（2.4 = 记号之后第一个字）
用户设置（字号 27px、行高 34 → 51px，extra = 16）
  dlineinfo("2.0")  = (189,  51,   0, 16,  8)   ← 空盒子
  dlineinfo("2.4")  = (219,  67, 540, 51, 36)   好
```

1. **空盒子的高度随行高设置变** → 判据**只能看宽度**（`box[2] > 0`）。
2. **空盒子的 `y` 比真正的文字上沿还高 `extra` 像素**（33 vs 35、51 vs 67）→
   量到好盒子就**直接用**，不要和空盒子「上沿取更靠上的那个」合并——合并会把序号
   往上顶 16 像素（跑到上一行），引用竖条也和上一段错开。
3. **空行、只有记号的行**返回的也是宽 0，但**盒子是对的**（`(237, 201, 0, 33, 25)`、
   `(189, 93, 0, 51, 36)`：y 接着上一行、高 = `px(行高)`、基线是真基线）→ 要**直接接受**，
   不能再量一次（`_visible_lines` 是滚动时每帧都走的热路径，空行又多）。

**修法**：删掉 `MIN_DISPLAY_LINE_H`，新增 `is_real_display_box(box, line_height)`，
判据 `box[2] > 0 or box[3] >= px(line_height)`——因为「空盒子高度 = 行高 − 行距」永远
**小于**行高，这一条刚好把「空行」和「折行的坏盒子」分开，且与字号、行高都无关。
`_display_line_box` 改用这个判据，量到好盒子直接返回；量不出来只剩空盒子时，空行照旧
返回、折行的行返回 `None`（照着空盒子画会在**上一行**位置凭空冒出一块序号，比不画还糟）。

**顺带修掉一个同类问题**：**视口下沿**那一显示行的盒子会被 Tk 裁一刀（`box[3]`
51 → 42、33 → 29），而 `box[1]` / `box[4]` 不裁。装饰画布照着裁过的 `box[3]` 定高，
贴在下沿那一行的序号下沿就切掉一条（实测画布高 24、序号需要 32，**切掉 8px**）。
新增 `_display_line_height()`（= `px(设置行高)`）当下限，序号画布与引用竖条都用它。
正常盒子的 `box[3]` 本来就等于它，所以对健康排版零影响。

## 2026-09-25 用户两项反馈（排序挪进右键菜单 / 隐藏预览栏滚动条）

### 真因：Tk 的 grid 是「一列宽 = 该列所有行里最宽的那个」

上一轮把「排序：按名称」放在文稿列表**标题行**的第 1 列。看着只占标题右边一点，
实际上：

- 面板 `cards_panel` 固定宽 `CARDS_W`（459px，`grid_propagate(False)`），**没变**；
- 但标题行多了一列，而 `cards_holder`（卡片画布）在第 1 行第 0 列，
  **grid 的列宽是所有行共用的**——第 1 列的宽度 = 那个标签的宽度 166px，
  于是卡片画布被挤成 `459 − 166 − 26（滚动条）= 267px`。

**实测（改前 → 改后）**：

```
预览栏面板      459  →  459      （面板本身一直没变）
卡片画布        267  →  459      （+192px，+72%）
编辑器画布      949  →  949      （本来就没被挤，用户的感觉来自卡片区变窄）
预览栏滚动条     26  →  无
标题行控件      [标题, 排序标签] → [标题]
```

### 改法

1. **排序挪进文稿列表的右键菜单**：`_add_sort_cascade(parent)` 往菜单末尾挂一个
   「排序：XXX」级联项（标签里直接写着当前用的是哪种，展开后当前那种带勾）。
   - 挂在 `_doc_menu` 末尾（右键某张卡片时能看到）；
   - 另外 `_on_cards_right_click` 里**点卡片下方的空白也弹菜单**——原来点空白什么都不
     发生，而文稿少的时候卡片之外全是空白，不给入口等于没有排序。空白处的菜单只有
     排序、没有针对某一篇的操作（`_sort_only_menu`）；回收站模式不弹（它有自己的顺序）。
   - 标题行只留「全部文稿」一个控件；`cards_holder` 顺手加上 `columnspan=2`，
     以后标题行再放东西也不会把卡片区挤窄。
   - `_sort_button_text` 改名 `_sort_label_text`（它现在喂的是菜单标签，不是按钮），
     `_on_sort_click` 删掉。
2. **预览栏不放滚动条**：`cards_holder` 里只留画布，`yscrollcommand` 一并去掉。
   滚轮是这一列唯一的滚动方式（`_on_cards_wheel` 本来就绑着）；
   `_on_cards_scrollbar` **保留**——它是程序化滚动的正规入口，也是
   `test_scrollbar_command_cannot_push_the_list_down` 直接调的对象，只是不再有控件调它。
   **编辑区的滚动条不动**（用户只说预览区）。

### 顺手修掉一条 flaky 测试

`test_sort_by_created_is_newest_first` 原来写死期望 `c, b, a`。但 **`os.utime` 改不了创建
时间**——Windows 上 `st_ctime` 就是创建时间，只能由系统在写文件那一刻记下来，
`_make` 里那三次 `utime` 对它毫无影响。三个文件的 ctime 是真实值、彼此只差几微秒，
文件系统时间戳精度不够时就会**相等**，而相等时 `sorted` 保持原顺序，写死的期望值就随机变红
（本地红过一次，之前跑绿是运气）。改成跟 `st_ctime` 的真实值对，并**新增一条**
`test_created_and_modified_use_different_timestamps` 把「用哪个字段」直接钉住
（把 mtime 拨到很久以前，created 排序不该受影响）。

### 问题：测试要建真窗口，就会抢前台

测试里大量断言依赖 Tk 的**真实几何**（`dlineinfo`、`winfo_width`、装饰画布的位置），
而这些只有窗口**真的被映射**了才量得出来——`withdraw()` 藏起来的窗口量不出任何东西。
代价是每跑一次全量测试，屏幕上要闪几百次窗口、焦点被抢几十次。用户在前台干活，这很烦。

试过但不够的两种办法（都实测过）：

| 办法 | 结果 |
| --- | --- |
| `geometry("1180x760+-4000+-4000")` 把窗口挪到屏幕外 | 几何是对的，但**窗口不绘制**：`GetDC(hwnd)+BitBlt` 抓回来一片纯色，`PrintWindow` 只画得出边框画不出正文；而且**焦点照样被抢** |
| `WS_EX_NOACTIVATE` | 挡不住（Tk 映射窗口时会激活它） |

### 解法：换一个 Windows 桌面

Windows 的**焦点是按桌面算的**——别的桌面上的窗口根本不可能抢走当前桌面的前台，
屏幕上也不会出现任何东西。同一个窗口站（WinSta0）里的另一个桌面照样有完整的 GDI 与合成能力。
`CreateDesktopW` + `STARTUPINFO.lpDesktop` 就能把子进程放进去，见新文件 `tools/quiet_desktop.py`。

`tools/run_tests.py` 因此多了一层：

- **默认在隐藏桌面上跑**：父进程 `CreateDesktopW`，子进程用 `--in-process` **原地**跑测试。
  **必须是原地跑**——`CreateDesktopW` 只对**直接**继承该桌面的进程生效，子进程若再
  `CreateProcess`，孙进程就回到默认桌面去了（`unittest.main` 也是新进程，同样不行，
  所以走的是 `unittest.TestLoader().discover(...)` + `TextTestRunner`）。
- `--foreground` 回到当前桌面：**截原生菜单必须用它**，理由见下。
- `-k <关键字>` 照旧过滤文件名。

### 两个「静默失败」顺手堵掉

1. **0 个用例也算成功**：unittest 对「一个都没跑到」判 OK，于是写错的 pattern 会以

### 8. 深色主题

**做法：重灌颜色常量 + 重建整个界面**，而不是逐个 `configure`。

- 全项目上百处都是在**建控件那一刻**读颜色的（`bg=CARD_BG`、
  `canvas.create_text(fill=TEXT)`…），逐个回溯去改既写不完也容易漏。
  而这些控件重建一遍只要几十毫秒，状态（文件夹、当前文稿、光标、滚动位置）都在
  `self` 上，重建完按原样恢复。所以：`THEME_KEYS`（45 个名字）+ `_DARK_COLORS`
  （深色覆盖值）+ `apply_theme(name)`（`globals().update()`）+ `_rebuild_ui()`。
- **`THEMES["light"]` 在导入时快照**。用户选了「只改界面，导出图保持浅色」，
  所以 `export_palette()` 只读那份快照，绝不读当前全局——否则切到深色之后
  导出图也会跟着变暗。
- **重建前必须 `root.unbind()`**：`_build_window` 里 `<Destroy>` 用的是 `add="+"`，
  不先解绑就会一层层叠上去。
- 顺手把**散在绘制代码里的 8 种硬编码颜色**收进调色板：`#EFEDE8`/`#F7F6F4`/`#F0EEE9`

  `#CFDDFB`（编辑区选区）、`#E8EFFC`（字体列表选中行）、`#FFFFFF`（选中卡片上的文字）。

#### 标签挂到哪一行——**踩了两次才量对**

第一版写的是 `tag_add("bottom_pad", "end-1c linestart", "end")`。截图看着没问题

被算两遍。

于是写了 `tools/_probe_pad_tag_range.py`，把「两种文稿结尾 × 若干候选范围」全量一遍。
量出来最有意思的一条是：**没有一种固定范围能同时覆盖两种文稿**——
Tk 的 Text 自己还额外带一个「隐形换行」，所以 `end-1c` 落在哪一行取决于文稿是不是
以换行结尾：

| 文稿结尾 | 能用的范围 | 换另一种会怎样 |
| --- | --- | --- |
| 以 `\n` 结尾 | `end-1c` → `end` | 只剩 8px（留白静默失效） |
| 不以 `\n` 结尾 | `end-1c linestart` → `end-1c lineend` | 只剩 8px（同上） |

两种都在 24.9% 留白。所以最终写成**按情形选范围**：

```python
start, stop = "end-1c linestart", "end-1c lineend"
if self.editor.compare(start, "==", stop):      # 末尾是空行 → 退回去包那个空行
    start, stop = "end-1c", "end"
self.editor.tag_add("bottom_pad", start, stop)
```

凡是靠标签几何生效的样式，都要有一个「量出来对不对」的探针，不能只看截图。

## 2026-09-25 导出长图随机增加换行（第 7 轮）

用户反馈一句话：**「导出长图时会有随机增加换行的问题」**。

### 根因：折行断点算法，两个缺陷叠在一起

`image_export._wrap` 逐字累加宽度，放不下时调 `_break_point` **一路往回找「上一个空格」**。
这条规则在两处出错：

| # | 形状 | 现象 |
| --- | --- | --- |
| ① | 断点落在**行首的空白**里 | 甩出一整行空白（`rstrip` 后为空）——**真的多一个换行** |
| ② | 中文行里那个空格在十几个字以前 | 白扔大半行（实测一行只填到 55%），常常因此多出一整行 |

① 的触发面很宽：Markdown 用**行尾两个空格**表示硬换行，编辑器里那些「续行」就带着
**两个前导空格**。这一批在用户自己的两份说明书里就有 136 + 56 = **192 行**。

### 改法

`_break_index(text, start, index)` 取代 `_break_point`，规则变成
**「从放不下的那个字往回扫，遇到的第一个『空格』或『宽字符』就是断点」**：

- 放不下的正好是空格 → 断在它后面（空格归上一行行尾，事后 `rstrip` 掉）；
- 放不下的是宽字符（中日韩）→ **直接断在它前面**（中文本来就能在任意字前断，且已是最紧）；
- 其余 → 往回扫，第一个空格或宽字符之后就是断点；
- 扫不到（超长西文单词）→ 按字硬断。

① 由「宽字符本身就是断点」天然避开（前导空格不再是唯一候选）；另加一条硬判据
`text[start:cut].strip()` 为空就作废该断点，退回按字断。

| --- | --- | --- |
| `_probe_export_wrap.py` 过早断行 | **154 / 551** | **9 / 502**（剩下的 9 全是「探针忘了算断点那个空格」） |
| `project.md` 显示行 / 总高 | 685 / 41442 px | **650 / 39342 px**（-35 行、-2100 px） |
| `project.md` 段内空行 / 续行以空格开头 | 4 / 8 | **0 / 0** |
| `project.md` 填充率最低 / <90% 的续行 | 0.0% / 102 | **81.8% / 4** |
| `简记使用说明.md` 显示行 / 总高 | 569 / 38124 px | **555 / 37284 px**（-14 行、-840 px） |
| `简记使用说明.md` 段内空行 | 13 | **0** |
| 全量测试（隐藏桌面） | 551 项 | **562 项 OK**，135.3 秒 |

## 2026-09-25 选中无序列表所在行也会自动换行（第 8 轮）

用户报：「修复选中无序列表所在行也会自动换行的问题」。

### 根因：两层，缺一层都修不掉

光标进到一行时，行首记号（`- ` / `* ` / `- [ ] ` / `> `）要从 `elide` 变成显示源码。

1. **宽度**：记号平时宽度 0，露出来就占「记号宽」（用户设置下 `- ` 20 px、
   `- [ ] ` 54 px），正文被顶右那么多、可用宽度也少那么多。
2. **更要命的是控件级折行方式是 `word`**。`word` 的规则是「一个词在当前显示行的
   **剩余**宽度里放不下，就整个挪到下一显示行」。正文平时就是这一显示行的第一个词，
   放不下只能在原地按字符断开；**记号一露出来，这一显示行就有内容了，正文那个词
   于是被整个挪到下一显示行**——显示行凭空多一行。

第 2 条是第一次没找到的那一层：**只补偿宽度（`lmargin1` 减掉记号宽）之后，折行位置和
显示行数一点没变**。所以第一版「补偿宽度」的修法在探针上完全看不出效果。

### 原始几何（用户设置 行宽 60 / 字号 18 / 行高 34；`- ` + 31 字正文）

| 状态 | 显示行 0 装了什么 | 正文首字符 | 显示行数 |
|---|---|---|---|
| 记号隐藏 | 正文第 2–21 字（x=219） | y=135 | **2** |
| 记号露出（只补偿宽度） | 只有 `- `（x=199，宽 20） | y=170（**下一显示行**） | **3** |
| 记号露出（补偿宽度 + `wrap=char`） | `- ` 占 199–219，正文第 2–21 字 **x=219** | y=119 | **2** |

### 修法

- 新增 `syntax_marker` 标签，**必须建在 `li{n}` 之后**——Tk 里后建的标签优先级更高，
  否则 `li{n}` 的 `lmargin` 会压过补偿值。
- 露源码时按 `_marker_options(indent)` 重新配置：`lmargin1 = 行缩进 − 记号宽度`、
  `lmargin2 = 行缩进`、`wrap = "char"`。正文位置与可用宽度都回到隐藏时的值。
- `_line_marks` 的记录从 4 元组变成 5 元组，第 5 项 `indent`（`None`，或已预算好的
  `(lmargin1, lmargin2)`）；`_swap_cursor_marks` 进这一行之前照着重新配置。
- **引用（`> `）走同一条路**：它有同一个毛病（画布竖条与无序列表共用
  `px(LIST_INDENT)` 这条缩进基准，补偿量算法完全一样），而光标行上画布装饰本来就不画，
  记号正好补上那个位置。有序列表**不动**（序号永远由画布画、记号永远 elide）。

### 1. 导出长图在逗号后换行——缺「禁则」

第 7 轮修的是**断点选取**（从放不下的字往回扫，第一个空格或宽字符处断），
但那支算法只看「哪里能断」，不看「断在哪里好不好看」：逗号/句号正好落在**行首**
是中文排版里的坏断行（禁则）。用户看到的「逗号后异常换行」就是**逗号被甩到下一行开头**，
它前面那个字孤零零留在上一行。

修法（`app/image_export.py`）：

- 新增 `_kinsoku(text, start, cut)`：断点若落在**收尾标点**（`，。、；：！？）》」』】…` 等）之前，
  就把断点**连同它前面那个字一起往前挪一格**（push-out），保证标点不在行首；
  开头标点（`（《「『【` 等）不许落在行尾，同理处理。
- **先 flatten 再 wrap**：`_wrap` 现在先把整行的行内分片摊平成一条纯文本再统一断行，
  避免「按片段各断各的」把断点又拉回片段边界；`floor` 定在**分片边界**上，
  保证 push-out 不会退到上一个片段里去。

核验 `tools/_check_export_wrap.py`：行首标点 / 行尾标点从 **10 / 1**（使用说明）与
**32 / 13**（project.md）降到 **0 / 0**。截图 `outputs/禁则修复{前,后}-{句号,逗号}.png`
（`tools/_shot_export_kinsoku.py`）。`tests/test_export.py` 新增 7 项（共 75 项）。

### 2. 编辑区底部留白「点击回车后闪回」——`spacing3` 标签滑出了最后一行

现象：底部 25% 呼吸空间**有概率消失**，而且**行号没变**，旧判据（只看末行行号）永远修不回来。

根因：`_apply_bottom_pad()` 给最后一行挂 `spacing3` 标签。末行是**空行**时标签范围是
`end-1c` → `end`（**只有那个换行符**）。在 `end-1c` 敲下第一个字时，Tk 把新字插在
**标签起点之前**（新字继承前一个字的标签 = 无），标签起点被顶到新字**之后**，
`spacing3` 落不到任何显示行上 → 留白静默失效（实测 267 px → 8 px）。删掉末行最后一个字是对称的。

`tools/_probe_pad_rule.py` 用「末行内容 × 标签范围」矩阵量出了**生效条件**：
**标签必须包含最后一行的行首**（`start <= "end-1c linestart" < stop`），换行符不算显示行字符。
实测 `61.0..62.0` 生效；`61.1..62.0`（起点被顶过新字）不生效；`60.3..62.0`（含 `61.0`）生效。

修法：判据从「末行行号变了没」改成 `_bottom_pad_covers_last_line()`——**量标签的真实范围**
（`tag_ranges` + `_index_pair`，字符串比大小是错的：`"61.10" < "61.2"`），不成立就重挂。
重挂后范围是 `行首..end`，之后敲的字落在范围**内部**，判据持续成立 → **每个新空末行只重挂一次**，
打字性能不受影响（`test_typing_a_run_of_characters_reapplies_the_pad_only_once`）。

### 3. 有序列表「光标选中该行即换行」——行内记号被露出来撑宽了整行

先证伪：有序列表**自己的序号是无辜的**。探针（`tools/_probe_bullet_wrap.py`，光标移开 vs 停在该行）
给出同一组盒子 `(23, 2, 219, 1044)`，序号永远由画布绘制、几何恒定。

真凶是**行内记号**（`**`、`` ` ``）：平时被 `elide`（零宽），光标一进该行就露出来，**整行变宽**；
`wrap="word"` 下「一个词在剩余宽度里放不下就整个挪到下一显示行」，行尾那个词被挤到下一显示行
= 用户看到的「换行」。`有序+粗体`、`无序+粗体`、`正文+粗体`、`有序+行内码`、`任务+粗体`、
`引用+粗体`、`标题+粗体` 全部复现。

修法 `_inline_reveal_fits(line_number, line)`：**只有整行带着记号量出来仍能放进一个显示行时才露**
（`_body_text_width(line) <= width - pad*2 - indent`）——精确判据：能放进一个显示行的行，
记号出现后仍然是一个显示行，几何完全不变；放不进的行本来就折行，就不露。
落点三处：`_swap_cursor_marks` 的 `reveal` 门（跳过 `off_tag=="syntax" and indent is None` 的条目，
行首记号条目 `indent is not None` 不受影响）、`_style_line` 在 `_tag_inline` 之后按同一判据调
`_hide_inline_marks`（整篇重解析时 `_tag_inline` 已加了 `syntax_current`）、
标题改走 `_tag_marker`（负 `lmargin1` 把 `# ` 挂进左留白；标题没有 `lmargin`，正文不动）。
**标题原来走 `_tag_syntax`**，那样条目 `indent is None` 会被行内门一起压掉，
所以测试里「`syntax_marker` 标签存在」那条才是抓回退的。

核验：`tools/_probe_bullet_wrap.py` 重写为 `dlineinfo` + `is_real_display_box` 量显示行，
**18 种行首记号形状 × 12 种长度 = 216 条，折行全等、0 条差异**；把 `_inline_reveal_fits`
强制返回 `True`（A/B）后立刻出现 **66 条差异**——证明这道门就是修复本身。
新增 12 项测试（`InlineMarkRevealTests` + `TallSettingsInlineMarkRevealTests` +
`HeadingMarkerWrapTests` + `TallSettingsHeadingMarkerWrapTests`）；撤掉修复验证：
`_inline_reveal_fits` → `True` 红 6 条。

## 2026-09-26 「导出长图逗号后异常换行」——真因是缩进续行没并进上一段（第 10 轮）

> 1. 在编辑页面，如果缩短行宽，逗号后面的文字也会自动换到新的一行，
>    而导出长图时，行宽很窄，所以会有异常换行的问题。

### 先证伪「行宽太窄」

用户把原因归到「导出图的行宽很窄」，所以先把行宽账量清楚：

- 导出图 1080px 宽、边距 72px、正文 32px → 内容宽 936px → **每行 29 个汉字**。
- 用户 7 篇文稿里有 3 篇过半的行超过 29 字（`新建-2026-09-20-201548.md` 39/65、
  `一、价值裂缝背后真正的问题.md` 68/91）。
- **1080px + 32px 这两条都不动时，每行上限就是 33 字**（边距得压到 12px）。
  实测（`tools/_probe_orphan.py`，真实渲染器）：

  | 边距 | 每行字数 | 折成多行的行数 | 短尾巴（尾行 <8 字） |
  |---|---|---|---|
  | 72（现状） | 29 | 140 | **45** |
  | 44 | 31 | 133 | 40 |
  | 24 | 32 | 130 | 41 |
  | 12 | 33 | 129 | 41 |

  收到 12px 只把短尾巴从 45 降到 41——**「加宽行宽」不是答案**。用户也明确说
  不要改图宽、不要缩字号。

### 真因：`build_export_rows` 把每一**源行**都当成一个独立块

Markdown 里列表项/段落写成长短两行、第二行缩进两格时，两行是**同一段**
（惰性续行）。`build_export_rows` 没做这件事——它逐行建 `Row`，于是

```
- **滚到底部会留一段空白**：长文滚到最底下时，最后一行下面空出约**四分之一屏**，
  光标停在末尾也还能看见「下一行」该在哪，不会贴着窗口下沿写。
```

被画成

```
• 滚到底部会留一段空白：长文滚到最底下时，最后一行下面空出
  约四分之一屏，          ← 这一项被从中间截断
光标停在末尾也还能看见「下一行」该在哪，不会贴着窗口下沿   ← 缩进丢了
写。
```

第一行末尾正好是个逗号，下一行起头是「光标停在…」——**「逗号后面的文字换到了
新的一行」**，一字不差。顺带：续行那两个前导空格被当成正文画了出来
（那一显示行只有 97.6% 填充，缺的 2.4% 就是那两个空格）。

规模：使用说明 509 行里 **60 行**是缩进续行，`project.md` 287 行里 **178 行**。

### 改法（`app/main.py` 的 `build_export_rows`）

加一个 `absorber`：上一行产生的、还能吞并续行的 `Row`。

- 当前行 `parse_block` 得 `text`、**行首有空白**、`absorber` 还在、
  且**上一行不是硬换行**（不以两个空格或 `\` 结尾）→ 并进 `absorber`，行首缩进去掉。
- `absorber` 只在 `text`/`bullet`/`task`/`ordered`/`quote` 之后保留；空行、标题、
  分隔线、代码块、表格之后一律清空（**`heading` 不吞续行**）。
- **缩进的 `- ` 是下一层列表项**（`parse_block` 给 `bullet`），不是续行，不会被吞。
- 拼接：两侧都不是中日韩字符（`ord > 0x2E80`）才补一个空格——英文折行要那个空格，
  中文之间不能插。
- **硬换行的续行不并**，但它行首的缩进同样去掉：那是排版空白，不该画成一小块留白。

## 2026-09-26 「引用中英混合/插入空格会换行 + 显示比例不对」——真因是编辑区 `wrap="word"`（第 11 轮）

### 1、2 是同一个 bug：Tk `wrap="word"` 把「空格后面那一串」当成一个词

Tk 的 `word` 折行规则是「**以空格分隔的一串字符 = 一个不可拆的词**」。中文整行**没有空格**时，
这个词就是整行，放不下只好退化成按字符断——**反而填得满**（实测 99.3%）；可只要行里出现**一个空格**
（自己敲的，或中英混排带出来的），空格后面那一长串中文就成了一个「词」：放不下就**整串挪到下一显示行**，
本行右边空掉一大块。这就是「引用有中英混合时会换行」「文字间插入空格会换行」——**两句其实是同一件事**。

实测（`tools/_probe_editor_wrap.py`，正文可用宽 571px，逐显示行量墨迹宽 ÷ 可用宽，
**去掉行尾那个被折行吃掉的分隔空格**）：

| 源行 | 第一显示行填充率 `word` → `char` | 显示行数 |
|---|---|---|
| `短 后面这一整串中文…`（最坏情况） | **4.7% → 96.0%** | 3 → 2 |
| `> 引用开头 English 后面这一整串中文…` | **41.9% → 100.0%** | 3 → 2 |
| `- 列表开头 English 后面这一整串中文…` | **41.9% → 100.0%** | 3 → 2 |
| 纯中文对照（整行无空格） | 99.3% → 99.3% | 不变 |

纯中文那行两种模式都是 99.3%——**说明量法本身是对的**，异常只出在「有空格」的行上。
探针按「填充率 < 90%」判异常：`word` 下 **4 处**、`char` 下 **0 处**。
（阈值取 90% 而不是 95%：折行点落在空格上时那一行本来就只有 94.6–95.6%，用 95% 会误报；
真正的 bug 是 4.7% / 41.9%，差一个数量级。）

一行改动，注释里把上面这套证据全写进去（防回退）。代价：**英文单词跨行时会被从中间断开**
（`wor|ds`）。中文优先的日记里这个代价可以接受，而且**导出长图本来就是按宽字符断行的**，
两边这才对得上。

## 2026-09-26 「编辑区显示比例」改成以屏幕为基准 + 软件最小宽度（第 12 轮）

> 1. 无论是否是在专注模式，当整个编辑区占屏幕比例超过内容行宽比例+10% 时，
>    文本区按设定的最高比例显示，两侧平均分配空白。
> 2. 当编辑区小于设定的内容行宽比例+10% 时，编辑区两侧始终各留 5%，进行等比例缩小。
>    软件最小宽度为屏幕比例的 40%。
>
> 例如：设定内容行宽为 50%，编辑区显示占屏幕比例大于等于 60% 时，编辑区两侧留白 5%。
> 当编辑区显示占屏幕比例为 40% 时，内容行宽为 30%，编辑区两侧留白 5%。

### 先把两条规则合成一个式子

设屏幕宽 S、**编辑区**宽 C、内容行宽比例 r。用户那两条其实是同一个式子的两端：

    正文块宽 T = min(r·S,  C − 2×5%·S)

- `C ≥ (r + 10%)·S` ⟺ `(C − r·S)/2 ≥ 5%·S` → 取第一项，T = r·S，两侧平分剩下的空白；
- 否则 → 取第二项，T = C − 10%·S，两侧各留 5%·S。

两边在 `C = (r + 10%)·S` 处**正好接上**，所以没有跳变（有一条测试专门钉这个接缝）。
实现就一行：`pad = max(0, (控件宽 − T) / 2)`。

### 问清楚了两件事（都影响很大）

1. 「屏幕」指**显示器**还是**应用窗口**？→ 用户选**显示器**。这条决定了「窗口没最大化时
   正文有多宽」：基准是屏幕时，窗口一缩正文就明显变窄。
2. 「软件最小宽度 = 屏幕的 40%」按字面算是 1024px，此时编辑区只剩约 300px、正文约 100px
   （一行 3 个汉字），几乎没法写作 → 用户选**「编辑区至少占屏幕 40%」**，于是
   窗口下限 = 导航栏 + 文稿列表 + 40%·S（本机 267+459+1024 = **1750px**）。

### 一个必须知道的副作用

三栏都开着时编辑区通常只占屏幕 40% 上下，**默认窗口就落在第二档**，那一档里

    正文块宽 = 编辑区宽 − 10%·屏幕宽

**和 `line_width` 完全无关**——也就是说默认窗口下行宽设置不起作用；要让设定值真的生效，
得把窗口拉到 `编辑区 ≥ (r+10%)·S`（r=50% 时窗口要约屏幕的九成宽），或者进专注模式。
这是规则本身的结果、不是 bug，专门写了一条测试把它钉住（`test_the_setting_is_inert_...`），
免得以后被当成故障「修掉」。也已经写进使用说明。

### 改法（都在 `app/main.py`）

- `_screen_width()`：读显示器宽。`_screen_width_override` 给测试/探针钉值用
  （同 `JIANJI_SCALE` 的思路，不然断言会随跑测试那台机器而变）。
- `_editor_target_width(column)`：算 T。基准用**编辑区**宽（含行号槽与滚动条）——
  「编辑区占屏幕比例」和「两侧各留 5%」说的都是编辑区。
- `_sync_editor_padding()`：`pad = (控件宽 − T) // 2`。
- `_apply_min_window_width()`：`minsize(NAV_W + CARDS_W + 40%·S, px(560))`。每次重排算一遍、
  值没变就返回——`minsize` 会触发 `<Configure>`，不设这道门会来回弹。
- `_build_window()`：初始宽度也不小于下限，否则窗口一建出来就被顶一下。

## 2026-09-28 三项反馈（选中末行阴影盖留白 / 长图每行 20 字 / 滚动时记号卡顿）

### 1. 选中最后一行的文字后，阴影会覆盖下面留白

**先证伪「留白算少了」**：留白按视口高度的 25% 算，量出来是对的，高度没问题。问题不在高度，在**它挂在哪一行上**。

**根因**：`dlineinfo` 返回的显示行盒子**把 `spacing1` / `spacing3` 一起算进高度**（和 `line_height` 同等对待），
而 Tk 画选中高亮画的正是这个盒子 —— 盒子多高，阴影就多高。底部留白是挂在「最后一行」上的 `spacing3`，
如果最后一行**有正文**，那个正文行的盒子就长成了一个「正文 + 25% 视口」的巨盒。

实测（用户设置：行宽 60 / 字号 18 / 行高 34；视口 1071px、留白 267px）：

| 文稿末尾 | 留白标签落点 | 选中阴影高 | 正文行下方可留白 | 结论 |
| --- | --- | --- | --- | --- |
| 没有换行符 | 正文行 `end-1c linestart..end` | 310px | 0px | ✗ 阴影把整块留白一起涂蓝 |
| 有一个 `\n` | 空行 `end-1c..end` | 51px | 310px | ✓ 干净 |
| 有两个 `\n` | 空行 | 51px | 310px | ✓ 干净 |

**看的是差值不是绝对值**：310 − 51 = 259 ≈ 留白值 267 —— 留白有多大，阴影就多出多大。
绝对值会随文稿内容与设置浮动，别当常量（判据一律写「阴影高 < 留白值」这种相对式）。

也就是说，**这个 bug 完全由「文稿末尾有没有换行符」决定**。翻用户 21 篇真文稿，**5 篇（24%）末尾没有换行**，
其中包含一篇 4.8KB 的 `开发记录.md` —— 不是罕见路径，是四分之一。

**六种标签摆法全量测过，没有一种能修**（记下来免得重走）：

| 标签范围 | 结果 |
| --- | --- |
| `end..end` | Tk 直接丢弃，`tag_ranges` 为空 → 留白**静默消失** |
| `end linestart..end` | 同上，被丢弃 |
| `end-1c..end` | 只盖住那个换行符，留白**静默消失**，盒子只剩行自身高 |
| `end-1c linestart..end-1c lineend` | 阴影照旧盖住留白 ✗ |
| `end-1c linestart..end` | 阴影照旧盖住留白 ✗ |
| 自绘选区（给标签设 `background`） | **标签底色一样盖住 spacing** ✗ |

结论：**没有任何标签摆法能修**。这不是摆放问题，是「留白和正文行不能落在同一行上」的结构问题。

**改法**（用户三选一，选了「文稿末尾自动补空行」）：载入时做一次字符串归一化。

`app/main.py` 新增 `_ensure_trailing_newline()`，并把它折进 `_load_editor_text` **已有的那一次 `insert`**：

```python
def _ensure_trailing_newline(self, text: str) -> str:
    if text and not text.endswith("\n"):
        return text + "\n"
    return text
```

```python
self.editor.insert("1.0", self._ensure_trailing_newline(text))
```

折在字符串上而不是「插完再 `insert("end", "\n")`」，有三个好处：不多发一次 `<<Modified>>`（否则打开一份文稿等于多跑一遍重解析）、
**不进撤销栈**（否则 Ctrl+Z 会先把留白用的空行撤掉）、不置脏标记（补的换行在 `edit_reset()` 之前就已经在缓冲区里了，
所以打开文稿不会立刻变脏、也不会平白触发一次存盘）。

**为什么不实时强制**：先试过在 `_apply_bottom_pad` 里发现末尾没换行就补一个，跑出 **29 个失败**
（20 个 `test_list_editing` + 1 个留白测试 + 8 个连带）。探针 `probe_list_return.py` 查到真因：
`editor.insert("end", "\n")` 会**把 `insert` 标记一起挪到新行**（1.6 → 2.0），于是 `_on_editor_return`
看到的是空行，返回 `None` 而不是 `"break"`，列表续号逻辑整条失效。
把光标存回来能修掉失败，但**实时强制本身是错的**：末尾那个空行会变成删不掉，退格在那里静默失效。
所以最终回到「载入时归一化」。

**有意留的残留**：用户手动删掉末尾那个换行符后**不再补**（补了就删不掉），此时留白会出现一个空洞，
重新打开文稿即恢复。已写进 `_apply_bottom_pad` 的 docstring。

**验证**：`shot_pad_pair.py` 两种状态各跑一次，前后对照：

### 3. 快速滑动文章时，有序标号和无序标号卡顿

**先量，不猜**。给一次真实滚动帧打点，按耗时排序：

| 调用 | 单次耗时 |
| --- | --- |
| `index("N.0 + 1 display lines")` | **200–436 µs** |
| `@0,y` | 19 µs |
| `dlineinfo` | **4 µs** |

`+ 1 display lines` 比 `dlineinfo` **贵 50–100 倍**，而一次重画里要调 7 次，其中 **6 次是白问**（合计约 1.6 ms，
占整帧三分之一）。`_visible_lines` 的 docstring 里早就写明「这个下标运算最贵、要避开」，主循环确实避开了，
**但 `_continuation_lines` 漏了** —— 它对每一行引用 / 表格都无条件调一次，而绝大多数行根本不折行。

**改法**：在 `_continuation_lines` 里先花两次便宜的 `dlineinfo` 问「这一行到底折没折」，折了才去走那条贵的路：

```python
first = self._display_line_box(f"{number}.0")
if first is None:
    return out
tail = self._display_line_box(f"{number}.end")
if tail is not None and tail[1] == first[1]:
    return out          # 首尾落在同一显示行上 = 这一行没折
```

有个坑必须处理：**末尾量不到时不能当成「没折」**（末行折到视口外面去了，`dlineinfo` 返回 `None`），
那种情况下前半截续行是可见的、竖条和表格框还得画，所以保留原来的精确路径兜底。

**效果**（`tools/_bench_perf.py 40`，1241 行文档）：

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| 一次滚动帧 | 6.6 ms | **2.8 ms** |
| `_redraw_margins` | 5.5 ms | **2.0 ms** |
| `_visible_lines` | 2.4 ms | **0.4 ms** |
| `_redraw_decorations` | 3.0 ms | **0.4 ms** |

**验证**：肉眼确认引用竖条仍覆盖全部折行、表格框完好。测试 `test_visible_lines_walk_logical_lines_only`
改写成更强的契约：夹具里的引用 / 表格都不折行，就**一次 `display lines` 推算都不该有**（原来只允许
`len(logical) + 2` 次 `dlineinfo`，现在放宽到 `+ 2×引用表格行`，因为那两次很便宜）。
另加一条前置断言：夹具里必须真的有引用 / 表格行，否则这条用例守不住东西。

**合成很慢**：中文实测 **3.52 字/秒**，两千字的日记要十来分钟。所以走
**后台线程 + 主线程 `root.after(300)` 轮询**（`_speech_job` / `_speech_poll`），
状态栏显示「正在合成语音…已用 N 秒」。实测 `export_audio` **0.03 秒返回**（桩函数睡 0.4 秒），
主线程没有被挡住；完成时状态栏「已导出音频：朗读核验.wav（约 36 秒）」并自动打开文件夹。
时长用 `wave` 模块读**真实头部**，不拿「字节数 ÷ 44100」估（那假设了固定格式）。
核验 `tools/probe_audio_export.py`（写出 338388 字节、22050 Hz 单声道 16 位、7.67 秒）。

### 2. 文件名跟随一级标题

**先说结论：不能做成「一存盘就按 H1 改名」。** 扫了一遍用户的真实文稿，反例一抓一把：

| 文件 | 第一行 | 照 H1 改名的后果 |
| --- | --- | --- |
| `2026-09-13.md` | `# 今日日记` | 变成 `今日日记.md` |
| `2026-09-14.md` | `# 今日日记` | 和上一篇**当场撞车** |
| `开发记录.md` | `# 简记优化记录` | 用户自己起的名字被换掉 |
| `说明书/简记使用说明.md` | `# 简记 · 使用说明` | 同上 |
| `新建-2026-09-13-215259.md` | 表格行（没有 H1） | — |

所以规则是：**只有标题相对「载入时」真的被改过才改名**。基准点 `self._title_at_load`
由 `_load_editor_text` 从正文第一行取（`_clear_editor` 清空）。这样
「打开老文稿只改正文」和「新建后不动占位标题」都不会动文件名，而
「把 `# 新建文档` 改成 `# 健身计划调整`」会立刻改名。

其余细节：

- **只认第一行**（`first_h1_title`）。开头先空一行、或者第一行是 `## 二级标题`、或者只写了 `# ` → 都不改名。
  标题被清空时**保持原名**（把文件叫成 `.md` 是谁也打不开的名字）。
- **禁字符换全角同形字**：`\ / : * ? " < > |` → `＼ ／ ： ＊ ？ ＂ ＜ ＞ ｜`。
  直接删掉会把 `第1章/第2节` 粘成 `第1章第2节`，两截读不出边界。控制字符删掉、连续空白压成一个空格、
  末尾的句点与空格削掉、超 80 字截断。
- **保留设备名看第一个点之前那一段**：`NUL.md` 在 Windows 上一样是保留的，
  下划线要插进那一段（`NUL_.md`）——加在末尾（`NUL.md_`）等于没改。
- **撞名走 `unique_path`**（`-2`、`-3`），绝不覆盖。只改大小写时不加序号（Windows 不区分大小写，
  `待办`→`待办` 不该变成 `待办-2.md`）。
- **改名在正文落盘之后**：改名失败只是状态栏一句「改名失败，文件名保持不变」，内容已经安全写进去了。
- `disk_signature` 改名后**仍然有效**（改名不动 mtime/size/digest），所以外部改动监测不会误报。

**顺手修掉一条被改名牵连的既有路径**：`move_document_to` / `delete_document` 都是
「先 `save_now` 再拿手里的 `path` 去干活」，改名会让那个 `path` 指向一个**已经不存在的名字**
（`move_to_trash` 会抛 `FileNotFoundError`，`move_to_folder` 也一样）。两处都补上
`if was_current: path = self.current_path`，并各写了一条回归测试。

核验 `tools/_probe_title_rename.py`（**27 项全过**，含上面每一个反例）+ `tests/test_title_rename.py`（39 项）。

### 顺带抓到一个测试基建的隐形地雷：`import main` 必须排在第一次 `Tk()` 之前

全量跑出 **3 条红**，全在量几何的用例上（`test_heading_labels` 的徽标位置、
`test_markdown_syntax.SpaceDelimitedWrapTests` 的折行填充率），而**单独跑那两个模块全绿**。

定位过程（每一步都有数据）：

| 跑法 | 结果 |
| --- | --- |

| 只跑 `test_audio_export` + 上面两个 | **3 红，且数字逐位相同（0.8980070339976554）** |

所以触发者是新加的 `tests/test_audio_export.py`，而且它**名字排在最前**、模块级探针
（`_probe = tk.Tk()`）写在 `import main` 之前。机制：

`main` **在导入时**声明进程 DPI 感知（`SetProcessDpiAwareness(2)`），
而 **Tk 是在第一次 `Tk()` 时按当时的 DPI 定下 `tk scaling` 的**。顺序反了，
Tk 就按「未声明感知」的 96 DPI 算缩放，之后声明也追不回来：

| | 先 import main | 先建 Tk 根（错的） |
| --- | --- | --- |
| `SCALE`（main 自己算的） | 1.5 | 1.5 |
| **`tk scaling`（Tk 自己算的）** | **1.998** | **1.332** |
| `_current_pad` | 80 | **48** |
| 标题徽标画布 | `place`，x=23 | **`''`（压根没放置）** |
| 第 3 行折行填充率 | 0.971 | **0.898**（卡在 0.90 判据下面） |

编辑区宽两态都是 949px —— 所以这**不是**「窗口没排好版」的偶发，而是**确定性的**。
复现脚本 `tools/_probe_scale_order.py`（同一份代码只换导入顺序，两组数都打出来）。

**两层修法**：

1. `tests/test_audio_export.py` 在模块级探针**之前**加一行 `import main`（跟上其他测试模块的惯例）；
2. `tools/run_tests.py` 的 `run_in_process()` 里，在**发现任何测试模块之前**先 `import main`。
   这才是真兜底——靠惯例挡不住下一个把探针写在前面的人，而这个坑的表征（几个量几何的用例红、
   单独跑全绿、数字还每次一样）极难从失败信息反推。

> 这也是为什么一开始差点判成「偶发 flaky」：单看失败信息，0.898 vs 0.90 只差 0.2%，
> 很像浮点/布局暂态。**是「数字逐位相同」这一点把它钉成了确定性**——
> 真 flaky 不会连小数位都一样。

## 2026-09-28 行内强调解析：两处「记号露源码」的修复

起因是重出说明书长图时，图上明晃晃写着四个星号。顺着查下去发现**同一段代码里有两个独立的坑**，
而且都是「不报错、只是画错」，靠人眼看长图才能发现。

### 坑一：判「这段强调能不能用」时把内容也算进去了

`_inline_spans` / `_tag_inline` 里，行内代码**先**跑并 claim 掉自己的区间；强调随后跑，
原来的判据是拿**整个匹配区间** `start..end`（含内容）去比 `blocked`：

```python
if blocked(start, end):      # ← 整段比
    continue
```

于是 `**未压缩的 \`.wav\`**` 整段失效——行内代码 claim 了 `.wav`，加粗的区间跟它重叠，
加粗被丢掉，**四个星号原样留在正文里**。

改成**只看那两对记号**：

```python
if any(blocked(left, right) for left, right in
       ((start, inner[0]), (inner[1], end)) if right > left):
```

| 写法 | 改前 | 改后 |
| --- | --- | --- |
| `**未压缩的 \`.wav\`**，体积不小…` | `('文件是**未压缩的 ', …)` + `('**，体积不小…', …)` | `('文件是', …)` `('未压缩的 ', bold)` `('.wav', code)` `('，体积不小…', …)` |

### 坑二：`finditer` 不重叠，反引号里的 `**` 会「吃掉」后面真那对记号

修完坑一，长图上**还有**两处漏星号。这次的反例是说明书自己写的：

```
- **念的是正文，不是 Markdown 源码**：`#`、`- `、`1. `、`> `、`**`、反引号这些记号都不会念出来；
  表格按行念…分隔线跳过。**屏幕上看到的、长图里排的、耳朵里听的，是同一套文字**。
```

`finditer` 的第一段匹配正常。第二段**从反引号里那个当例子写的 `**` 开头**，
把后面「真的加粗」那对星号当成自己的**收尾**：

```
match (11, 28) '**`、后面还有 **真的加粗**'   inner '`、后面还有 **真的加粗'
```

这段匹配的开头落在代码区间里 → 整段丢掉，而**真正的那对加粗从没被匹配过**。
修法是**被挡下时从 `start + 1` 重新搜**（`search` + 手动推进），退回到真正的那个开头：

```python
search_from = 0
while True:
    match = pattern.search(line, search_from)
    if match is None: break
    start, end = match.span()
    inner = (match.start(1), match.end(1))
    if any(blocked(left, right) for left, right in
           ((start, inner[0]), (inner[1], end)) if right > left):
        search_from = start + 1      # ← 只跳过这个开头，别丢掉整段
        continue
    apply(tag, inner, (start, end))
    search_from = end
```

两处修法在 `_inline_spans`（导出长图 / 音频）和 `_tag_inline`（编辑区）里**必须一字不差**，
注释里互相点名——否则同一行文字在屏幕上一个样、导出的长图另一个样。

### 坑三（**不修**）：跨源行的行内记号

说明书里还有两处是**我自己写错了**：加粗的 `**` 开头和结尾被写在了两个源行上。
实测（`probe_split.py`）：编辑器与导出**两边都**把 `**` 原样显示——

```
line 1: syntax 记号 = ['- ']   该行文字 = '- 前缀**把第一行的'
line 2: syntax 记号 = []       该行文字 = '  存盘后文件名就跟着改了**（见说明）。'
bold 标签范围 = ()
导出侧： bullet [('前缀**把第一行的', False), ('存盘后文件名就跟着改了**（见说明）。', False)]
```

**屏幕和长图是一致的**，所以这**不是**导出链路的 bug，而是解析器本来就**逐行**工作
（增量高亮按行做，这是设计前提）。既然一致，就不能去改 `_append_continuation`
把合并后的段落重解析——那会让「屏幕上看到的、长图里排的、耳朵里听的，是同一套文字」
这条自己刚写进说明书的不变量当场失效。

所以这一条**只改文档**：

1. 把说明书那两处改成「记号开闭在同一行」，折行交给显示；
2. 在「补充说明」里**明写这条规则**（用户会遇到，之前没写）。

> 顺带发现：说明书里用双反引号写 `` `代码` `` 会露反引号——`INLINE_CODE_RE` 只认单反引号
> （`` `([^`\n]+?)` ``）。改成「行内代码（反引号）」这种说法绕开，没有为它加语法。

## 文件名无条件跟随一级标题（用户报「我改了标题，文件名没跟着改」）

### 先把症状坐实：不是代码坏了，是规则漏了一类文稿

用户两次提同一件事，第二次带了症状：

> 现在我修改第一行标题时，对应的文件名没有改变。实现每次第一行一级标题改变时都修改文件名。

先在用户真实文稿文件夹里对了一遍时间线，症状立刻清楚：

| 文件 | mtime | H1 | 名字跟上没有 |
| --- | --- | --- | --- |
| `测试文件名.md` | 09-28 20:43 | `# 测试文件名` | ✅ 跟上了 |
| `新建-2026-09-28-160555.md` | 09-28 20:07 | `# All in One 软件思考` | ❌ 没跟上 |
| `新建-2026-09-28-141548.md` | 09-28 20:10 | `# 待办` | ❌ 没跟上 |
| `新建-2026-09-28-153817.md` | 09-28 20:44 | `# 20260927广州草莓音乐节记录` | ❌ 没跟上 |
| `新建-2026-09-24-213637.md` | 09-26 22:51 | `# 健身计划调整` | ❌ 没跟上 |

关键在文件名里的时间戳：`新建-2026-09-28-160555.md` 是 **16:05:55** 建的，而改名功能
是 **17:25** 才提交的（`a442e8c`）。这批 `新建-*` 文稿**全部建在功能上线之前**，名字与
标题从此错位；`测试文件名.md` 建在功能上线之后，所以跟上了。

于是用户遇到的是：打开一篇 `新建-*`，把标题**重新敲一遍**（内容一字未变），存盘——
旧规则判「标题相对载入没变过」，文件名纹丝不动。**在用户眼里就是「改了标题，名字没跟着改」。**

### 规则改成一句话

`_follow_title` 原来的门是 `title is None or title == self._title_at_load`，现在只剩前半句：

```python
title = first_h1_title(text)
if title is None:
    return path
stem = title_to_filename(title)
if stem is None or stem == path.stem:      # 名字已经对了，不必动盘
    return path
```

即 **「第一行是一级标题，且清出来的名字与现在的文件名不一样，就改」**。代价是打开一篇
名字与标题本来就不一致的老文稿、只动正文，名字也会被扶正——这正是「文件名＝一级标题」
这条规则的应有之义，而且**只在存盘时发生**：光翻看不改，一个字都不落盘。

`_title_at_load` 这个基准点就此作废，连带三处引用（`__init__` / `_load_editor_text` /
`_clear_editor`）一起删掉，换成一个只在失败时才写的 `_rename_failed_for`：

```python
key = (os.path.normcase(str(path)), stem)
if self._rename_failed_for == key:
    return path                            # 同一个文件、同一个目标不再重试
...
except OSError:
    self._rename_failed_for = key          # 失败记一笔，别每次自动保存都提示一遍
```

`key` 里带上 `stem` 而不是只带路径：换个标题（换个目标名字）要能重新试，
不被上一次的失败连坐。

### 撞名的实际后果（在用户文稿上算过）

无条件规则下，用户 14 篇根目录文稿里有 **10 篇会被扶正**，其中：

  （两篇 H1 都是 `# 今日日记`，靠 `unique_path` 加序号，**两份正文都在，谁也没被覆盖**）；

- `说明书\简记使用说明.md` → `简记 · 使用说明.md`。

最后一条会**打断 `tools/_sync_manual.py`**（目标路径写死的）。所以顺手把它改成按 H1 推算：

```python

    """目标文件名主干：已经存在的那一份优先，其次按正文第一行的 H1 推算。"""
```

并在落盘后清掉**另一种主干**留下的孤儿分张（`{stem, LEGACY_STEM} - {stem}` 那一套 glob），
免得改过名之后旧名字的 png 留在文件夹里当幽灵。
