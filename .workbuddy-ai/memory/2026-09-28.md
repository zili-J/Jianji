# 2026-09-28

用户一次提了三个问题：① 选中最后一行时高亮盖住底部留白；② 导出长图改成每行 20 个字；
③ 快速滑动时有序/无序标号卡顿。三条都做完，643 个测试通过。

## ① 选中最后一行盖住留白 → 正文末尾补一个空行

**根因**：底部留白是挂在最后一行上的 `spacing3`，而 Tk 画选中高亮时把**整个显示行盒子**
（含 `spacing3`）一起涂色。留白挂在**正文行**上才会被盖住；挂在**末尾空行**上就不会。

**只有「文件不以换行结尾」时才踩到**（那时 `end-1c` 落在正文行上）：
实测（用户设置，视口 1071px、留白 267px）末尾无换行 → 选中阴影 **310px**（= 留白 267 + 行自身高）；
末尾有换行 → **51px**（干净）。**两者相差 ≈ 留白值**（310 − 51 = 259 ≈ 267）——
留白有多大，阴影就多出多大；绝对值随文稿与设置浮动，**判据别写绝对像素**。
用户文稿 21 份里有 **5 份**末尾没有换行（含一份 4.8KB 的 `开发记录.md`）。

**逐种标签摆法都试过，没有一条能修**（都在隐藏桌面上实测）：

| 摆法 | 结果 |
| --- | --- |
| `end-1c linestart`..`end-1c lineend`（原写法） | 留白在，但阴影把留白一起盖住 |
| `end`..`end`、`end linestart`..`end` | Tk 直接丢掉空区间，`tag_ranges` 为空、留白整段失效 |
| `end-1c`..`end` | 标签只盖住换行符，**留白同样失效**（行盒只剩行自身高、没有空白） |
| `end-1c linestart`..`end` | 跨两行，阴影照旧盖住留白 |
| 标签的 `background`（想自己画选中高亮） | 一样盖住留白，这条路也堵死 |

**两条出路**：把留白挪出正文区（`editor.grid_configure(pady=(0, pad))`，结构上免疫，
代价是编辑区**常驻**少 25% 视口 = 少看约 8 行），或让正文末尾始终有一个空行。
问过用户，选了后者（「文稿末尾自动补空行」）。

**实现**：`_ensure_trailing_newline(text)` 是**字符串级**的，拼进 `_load_editor_text` 那一次
`insert` 的入参里 —— 不要「先 insert 正文、再 insert 一个换行」：那会多发一次
`<<Modified>>`，等于打开一份文稿多跑一遍重解析。补在 `edit_reset()` 之前，
所以不进撤销栈、也不算用户改动（`open_file` 后 `dirty` 仍是 False，不会平白触发存盘）。

**中途试过又撤掉的写法（别再试）**：把补空行放进 `_apply_bottom_pad` 里「删了就补回来」。
它确实能堵住下面那条漏网路径，但代价是**末尾那个空行再也删不掉**——用户在那里按
Backspace 会静默失效（删掉 → 立刻补回，界面一动不动），比「只在选中时才出现的观感问题」
更烦人；而且它让 20 个 `test_list_editing` 用例红（那些用例断言正文内容，补了换行就不等）。
**顺带踩到**：`editor.insert("end", "\n")` 会把 `insert` 标记一起推到新空行上
（光标 1.6 → 2.0），接着敲的字就落到下一行去了 —— 补的时候必须自己存下光标再还原。

**残留（已知、有意）**：用户把末尾换行删掉（Backspace 并到上一行、整段删末尾、粘贴替换）后，
标签退回正文行，高亮又会盖住留白 —— 重新打开文稿自动恢复。见 `_apply_bottom_pad` 的注释。

## ② 长图每行 20 个汉字 → `DEFAULT_BODY_SIZE` 32 → 46

汉字在这几款中文字体里的**步进正好等于字号**（实测 霞鹜文楷 / 微软雅黑 / 雅黑 UI 都是
字号 32 → 单字宽 32px）。所以 `一行几个字 = (1080 − 72×2) ÷ 字号`：

| 字号 | 一行几个汉字 |
| --- | --- |
| 32（原来） | 29.25 → 29 |
| 46 | **20.35 → 20** ✓ |
| 47 | 19.91 → 19 ✗（20 个字要 940px，差 4px 放不下） |

所以是 **46，不是 47**，注释里写明了「别再往上调一档」。行距由 `_export_options` 按
`ratio = 46 / font_size` 推出来，用户设置下 60 → 87px。使用说明长图从 1080×31485 + 804
变成 **1080×31588 + 1080×21310（两张）**。

## ③ 滚动卡顿 → `_continuation_lines` 加便宜的早退

**元凶是 `index("N.0 + 1 display lines")`**：实测它 **200–436 µs 一次**，而
`dlineinfo` 只要 **4 µs**、`@0,y` 只要 19 µs。`_visible_lines` 的注释早就写明这个运算最贵、
主循环已经躲开了，但 `_continuation_lines`（展开引用/表格的续行）**每次调用都先问一次**，
而视口里绝大多数引用/表格行根本不折 —— 一次滚动重画里 7 次调用有 6 次是白问 ≈ 1.6 ms。

修法：先花两次便宜的 `dlineinfo`（首行 vs 行尾）判「折没折」，不折就直接返回。
**行尾量不到（折到视口外面去了）时必须退回原来那条精确的路**，不能当成「没折」——
那种情况下前半截续行是可见的，竖条/表格框还得画。

效果（`tools/_bench_perf.py 40`，1241 行文档）：

| 项目 | 改前 | 改后 |
| --- | --- | --- |
| 滚动一格 + 重画 | 6.6 ms | **2.8 ms** |
| `_redraw_margins()` | 5.5 ms | **2.0 ms** |
| `_visible_lines()` | 2.4 ms | **0.4 ms** |
| `_redraw_decorations()` | 3.0 ms | **0.4 ms** |
| `_redraw_line_numbers()` | 3.2 ms | 1.9 ms |

剩下最贵的是行号那 32 次 `create_text`（约 1.5 ms）—— 顺手验过「传命名字体
`tkfont.Font` 代替字体元组」**没有用**（0.72 vs 0.74 ms，Tk 自己会缓存字体描述），
所以没改。

## 截选区时的两个坑（都踩了，都很值钱）

- **`end-1c` 是最后一个真字符，末尾那个 `\n` 是 Tk 的幻影换行**。所以
  `get("end-3c", "end")` 会比正文多出一个 `\n`；`delete("end-1c")` 删的是**最后一个真字符**
  而不是「末尾换行」—— 想复刻「末尾无换行」的状态时，它会静默删掉「。」这种内容字符，
  于是截出来还是「有换行」的样子，白折腾一轮。**要造那个状态就直接 `insert` 原始正文**
  （`delete("1.0","end")` + `insert("1.0", RAW)`），别做「载入后再删一个字符」。
- **隐藏桌面上窗口拿不到键盘焦点，Tk 就不画选区底色**。第一版截图出来正文一点蓝色都没有，
  差点当成「问题不存在」；量出来的盒子高（310px）才是真相。**截选区前必须
  `root.focus_force()` + `editor.focus_force()`**（打印 `editor.focus_get() is editor` 确认），
  否则 `capture_widget_region` 截到的是一张没有选区的图。

# 2026-09-28（第四轮）git 远端：能加、不能推

## 证据链（别浪费时间重试）

- `~/.gitconfig` 只有 `[credential "helperselector"] selected = manager`；
  `C:\Program Files\Git\etc\gitconfig` 是 `credential.helper = manager` ⇒ 走 GCM。
- 环境里 **`GIT_TERMINAL_PROMPT=0` 是全局设的** ⇒ 不显式打开就永远等不到输入。
  显式关掉后 `git credential-manager get` **exit 124（超时挂住）**：GCM 想弹登录窗，
  沙箱里弹不出来，`git-remote-https.exe` 就那么等着。
- 有几次整个进程树被 **SIGTERM 硬杀**，连 `echo` 都不执行 —— 这是沙箱级 kill，
  不是 git 报错，别照着 git 的思路查。
- 还发现 `http_proxy/https_proxy = http://127.0.0.1:12653`（沙箱代理）。只读请求放行。

## 结论与交付

- 认证这一步**必须在用户自己的窗口里点一次**。
- 交付 `push_backup.cmd`（工程根，和 `run_jianji.cmd` 同风格）：打印远端/分支/待推提交 →
  `git push -u origin <当前分支>` → 失败给常见原因。第一次弹 GitHub 登录窗，
  登录一次后凭据进凭据管理器，**之后助手也能直接推**。
- **端到端验过**：临时建本地裸仓库、把副本里 `origin` 换成它跑通
  （`* [new branch] main -> main`、裸仓库 `refs/heads/main` = a442e8c），
  跑完清掉临时远端与裸仓库、`origin` 还原。`git remote remove` 会自动清 `branch.main.*`，
  不用手动收拾。

## 顺带修掉：`.cmd` 被 `.gitattributes` 转成了 LF

上一轮 `* text=auto eol=lf` 把 **`run_jianji.cmd`（用户双击的主入口）**也改成了 LF。
cmd.exe 对 LF 结尾的批处理容忍度有限（`goto :label` 会失效），入口文件不能赌。
补 `*.cmd text eol=crlf` / `*.bat text eol=crlf`（**必须排在 `*` 之后**，后匹配覆盖先匹配），
再把工作区文件显式转回 CRLF —— **git 只在检出时按属性改写，已存在的文件不会自己变**。
判据 `git ls-files --eol <file>` 应该是 `i/lf  w/crlf  attr/text eol=crlf`。

**`.cmd` 里写中文会乱码**（git 输出 UTF-8，cmd 按 936 渲染）→ 加 `chcp 65001 >nul`。
副作用：cmd 自己的提示语（`pause` 的「请按任意键继续」）变英文，取 git 输出这一头。
**`.cmd` 文件本身保持纯 ASCII**（`run_jianji.cmd` 早就这么做了，照它来）。
